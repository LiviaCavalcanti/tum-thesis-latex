\subsection{Prompt Sensitivity and Patch-Level Evaluation}
To evaluate prompt sensitivity, two configurations of the agentic pipeline were compared. They share the same parameters: the model (gpt-4o), the retrieved example, the target code, and the dataset split. 

\begin{itemize}
    \item \texttt{single\_turn}: few-shot marker prompt from the prompt registry (\texttt{single\_turn.py}).
    \item \texttt{tool\_calling}: ReAct prompt framework (\texttt{\_SYSTEM\_PROMPT}) combined with auxiliary reviewing code tools (\texttt{tool\_calling.py}).
\end{itemize}

Comparing these two different fingerprints per record using surface metrics, \texttt{BLEU/ROUGE/Jaccard}, the analysis shows similar results across the two strategies.
However, this similarity is not a consequence of a similar patch quality.
Rather, this occurs because the metrics get saturated by the outputs dominated by the unchanged code body.

To have better insights, the evaluation will also consider the hunk metric.
When analyzing the patch difference of the patches generated by the \texttt{CodeBERT\_seq} retriever pipeline, for example, we can see that the fix regions differ.
Patch hunk metrics demonstrate that the \texttt{tool\_calling} agentic approach outperforms \texttt{single\_turn}, improving \texttt{hunk\_token\_jaccard} from $5\%$ to $15\%$ and increasing \texttt{hunk\_removed\_f1} by $+0.17$.
These results indicate that evaluating prompt variations and control-flow strategies requires patch-isolated metrics to clearly evaluate fix quality.

Similarly, applying the hunk metric evaluation to the ensemble retriever pipeline, we can notice that it indicates a high rate of wrong patches (\texttt{hunk\_added\_f1 $\thickapprox$ 0.02}). 
It occurs from the fact that the patches just reproduce the vulnerable input. 
Analyzing the pipeline a step earlier, the retrieval performance is poor with only a 29\% CWE-match rate. %, which suggests that it is important to have a good retrieval. 
Consequently, even though the agent workflow verifies the correctness of the retrieved CVE for the code snippet under analysis, downstream LLM patch generation cannot easily recover from initial retrieval errors, corroborating the importance of robust (context?) retrieval for effective automated repair. 


\subsection{File vs. Method}
After investigation, I found that the method graphs were actually degenerated, that is, Joern was not able to understand the code elements 
resulting in a graph of unique node element, containing the whole code and edges have as source the node but the other end is null.
This behavior could result from the lack of the definition of all elements definition, making it dificult for the joern create the graphs.

Because the dataset also contain the file, we've done a comparison of the performance using the file and the method as input.

The results are in the Table~\ref{tab:cvefixes_file_method}. 
They show that file-level graphs outperform the method-level graphs, especially for the combined embedder for which $\text{hit@1}$ jumps from 0.333 to 0.889 ($+0.556$), and mrr jumps from 0.454 to 0.944 ($+0.491$).
\texttt{CodeBERT\_pattern} $\text{hit@1}$ increases from 0.678 to 0.889 ($+0.211$).
\texttt{CodeBERT\_seq} has a more modest $\text{hit@1}$ improvement from 0.722 to 0.889 ($+0.167$).
These improvements shows that the extra content encoded in the file-level graph bring important context wich may include global variables, imports, and cross-method, resulting in structures that leads to a better vulnerability identification.
This improvements make that the final performance of the embedders are equivalent. 
This allows us to conclude that enough context information allows a simple embedder of graph topographic description to perform equivalently to a semantic level pretrained model.
