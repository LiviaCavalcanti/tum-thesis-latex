As seen in Table \ref{tab:pca_l2}, $L_2$-normalization is an important component for the retrieval performance, whereas PCA produces a marginal but consistent change across the embedding metrics.
For the Topological Structure embedder, removing PCA results in a slight performance drop from 0.822 to 0.808 in hit@1 (and from 0.860 to 0.844 in MRR), indicating that PCA helps balance the concatenated GIN and WL representations. In contrast, removing $L_2$-normalization causes a severe degradation across all graph-based embedders, reducing Topological Structure hit@1 to 0.136 and GIN to 0.055, confirming that vector magnitude scaling is essential before computing distance metrics.

To investigate why removing $L_2$-normalization causes such a performance collapse, we analyzed the effective dimensionality of the resulting embedding space. 
Without $L_2$-normalization, raw 768-dimensional CodeBERT output vectors vary in magnitude. 
These scale differences can dominate the distance metrics when the vectors are compressed to 128 dimensions via PCA, masking directional semantics and restricting the embedding space into roughly three effective dimensions (3.13). 
On the other hand, applying $L_2$-normalization forces all vectors onto a unit hypersphere, eliminating magnitude variance so that distance calculations depend strictly on vector orientation. 
This keeps the semantic signal spread across nearly 16 effective dimensions (15.79), thereby preserving CodeBERT's representations and achieving the best retrieval performance (87.7\% hit@1).

While the Semantic embedder achieves the highest overall retrieval performance (Hit@1=0.877), the unsupervised Topological Structure embedder performs competitively (Hit@1=0.822) without relying on pretrained transformer architectures. 
This is especially relevant because topological graphs depend on structural invariants rather than code natural language and can be computed efficiently on CPU-only infrastructure.
Furthermore, structural embedders can be an alternative for rare, legacy, or domain-specific languages where pretrained models lack coverage.
Given that this baseline is completely unsupervised, supervised fine-tuning of lightweight graph neural networks presents a viable, compute-efficient strategy to surpass transformer-based retrieval baselines without requiring dedicated GPU infrastructure.
Therefore, a viable direction for future work is to train GIN as an alternative for out-of-distribution codebases, which can simultaneously explore the emergence of graph representation patterns that better capture vulnerabilities across a larger dimensional region, currently limited to  2.19, with PCA, and 6.83, without PCA.

However, domain-level analysis demonstrates distinct architectural strengths across vulnerability types.
For the \textit{Concurrency} category, the Topological embedder reaches perfect accuracy across all queries (100.0\% CVE and CWE hit rates), outperforming the Semantic model (92.3\%). Concurrency flaws—such as race conditions and deadlocks—depend heavily on inter-thread execution order, control-flow branching (CFG), and data dependencies (PDG), which are explicitly captured by Code Property Graphs but blurred in linear token sequences.
    
For \textit{Memory Safety} (78.6\% vs.\ 82.1\% CVE) and \textit{Resource Management} (83.3\% vs.\ 91.7\% CVE), the Semantic model holds the advantage. While pointer lifetime issues like \textit{Use After Free} favor graph topology, localized guard additions (such as null-pointer checks or resource cleanup flags) introduce distinct token-level cues that sequence transformers detect more effectively than global graph structures.
    
Both embedder families achieve identical 77.8\% CVE retrieval accuracy (and 88.9\% CWE accuracy) on \textit{Numeric/Type} vulnerabilities (e.g., integer overflows), demonstrating equivalent capabilities in capturing scalar arithmetic bounds.

Because logic flaws and input-validation bugs stem from domain-specific semantic context rather than structural anomaly or control-flow irregularities, structural graph abstractions lack the semantic depth required to index them effectively.


These results confirm that while sequence-based semantic embedders excel at localized syntax and high-level logic checks, structural graph embedders provide an essential specialized representation for execution- and control-dependent vulnerability patterns.

\section{CVEFixes: Embedder Retrieval Performance}\label{sec:cvefixes-retrieval}
As with the AutoPatch results, the CodeBERT-based retrievers outperform the Topological Structure embedding model. This suggests that for these real-world scenarios, the underlying semantic signal carries more weight than the aggregated code topological structure representations crafted under the settings used in this work.

\paragraph{Semantic + Structure Performance}
For the Semantic + Structure Retriever, Figure~\ref{img:retrieval_boxplots} shows that vulnerability classes such as CWE-190 and CWE-787 exhibit clear, distinct separations with no overlap between the interquartile ranges (IQRs) or whiskers of incorrect and correct matches. However, an exception occurs in CWE-20, where the ranking scores for incorrect retrievals are concentrated at higher values than the correct ones.

For CWE-476, while correct matches score slightly higher on average, their distributions noticeably overlap, lacking a clean separation. CWE-362 demonstrates a similarly fuzzy boundary. While the IQR for errors is mainly in the lower half of the correct ranking score distribution, the 25th percentile (p25) of correct retrievals aligns with the median of incorrect retrievals.

CWE-416 presents a challenging scenario. The incorrect retrievals exhibit a higher IQR, with its upper quartile significantly overlapping the correct score distribution. In practice, this wide variance means the retriever frequently ranks incorrect queries as highly as correct ones. Because the 75th percentile (p75) of the incorrect scores remains below the maximum of the correct distribution, yet still overlaps with its range, establishing a reliable classification threshold without losses is impossible in this case.

\paragraph{Semantic Retriever Performance}
The Semantic Retriever model exhibits a similar trend but with some differences. 
For CWE-362, the incorrect retrievals have a wider IQR and a higher median than the Semantic and Structure model. 
Additionally, the Semantic model shows a broader spread for correct matches in CWE-416 and CWE-476. Generally, the Semantic model tends to assign higher overall ranking scores, which can amplify false positives. 
Despite this, for both Semantic and Structure, and Semantic-only models, the median ranking score for a correct match remains consistently higher than that of an error for the majority of categories.

\paragraph{Topological Structure Model Performance}
In contrast, the Topological Structure retriever suffers from compressed ranking scores.
While Semantic and Structure, and Semantic-only models successfully cluster correct matches in the 0.6 to 1.0 range, the Topological Structure approach condenses almost all scores in between 0.2 and 0.5.

\paragraph{Vulnerability-Specific Challenges}
The semantic models perform particularly well for CWE-190 and CWE-787. In these categories, correct matches cluster at high scores with narrow IQRs, while errors remain isolated as low-scoring distributions. 
This suggests these specific vulnerabilities possess distinct lexical signatures that CodeBERT can capture.

Conversely, the models struggle significantly with other CWEs.
The CWE-362 (Race Conditions) IQR overlap between correct matches and errors indicates the models struggle to differentiate between safe and unsafe concurrent code operations.
Additionally, the Semantic model exhibits a wide IQR for CWE-476 (NULL Pointer Dereference) errors, and its median is close to the correct match median. 
This high volume of high-ranking false positives likely occurs because a vulnerable missing null check appears textually and sequentially identical to safe code in which a null check is unnecessary.

\subsection{CWE level analysis}

Evaluating retrieval performance across vulnerability classes reveals that structural and semantic embedders exhibit distinct and complementary failure modes depending on whether a weakness is localized to AST subgraphs or distributed across inter-procedural state and synchronization logic.

\paragraph{Localized Structural Invariance and Inter-Procedural Vulnerability Patterns}
Structure + Semantic model achieves good performance in retrieving localized data-flow and bounds-check patterns (CWE-20: Improper Input Validation and CWE-190: Integer Overflow). 
For example, localized input validation and array-indexing guards (CVE-2021-26788, $MAP=0.93$; CVE-2020-15211, $MAP=0.73$), the structural component captures the vulnerability on AST conditional nodes and local basic-block boundaries. 
Good performance is also observed when the patch involves modifying existing control constructs, such as reordering statement nodes or adjusting conditional predicates in concurrency guards (CWE-362: Race Conditions, e.g., CVE-2011-1768).

On the other hand, non-local semantic weaknesses, where the vulnerability stems from missing synchronization logic rather than existing control-flow nodes (CWE-362), show low performance. 
To illustrate, there are the following instances:
\begin{itemize}
    \item Complex Concurrency and Race Conditions (CWE-362): Multi-threaded race conditions (e.g., double-fetch bugs in kernel ioctls like CVE-2020-12652 or callback destruction races in network stacks like CVE-2021-32686; both $\text{MAP}=0.0$) depend on inter-procedural execution order and implicit timing invariants. Because AST and static graph embeddings inspect local function boundaries, they cannot capture missing inter-function synchronization mechanisms.
    \item CVE-2021-32686 ($\text{MAP}=0.0$, $n=1$): A race condition between socket destroy and callback in PJSIP TLS connections.
\end{itemize}

These vulnerabilities depend on execution order and synchronization across functions, which AST- or graph-structural embeddings cannot capture in the current setting. 
A similar case occurs with a Use-After-Free (CWE-416) CVE-2023-38703 ($\text{MAP}=0.0$, $n=2$), where the issue is caused by a lack of synchronization between the high-level SRTP transport and the lower-level media transport.

Another failure case stems from the lack of access to external configuration flags and runtime state invariants, as seen in (CWE-476) CVE-2020-10739 ($\text{MAP}=0.0$, $n=3$), where a Null Pointer Exception in Istio/Envoy was triggered under the Telemetry v2 configuration.

Broad refactoring or multi-file architectural changes, such as locking macros or structural realignment in (CWE-476) CVE-2020-35538 and (CWE-362) CVE-2012-3552, also show low performance (MAP < 0.5).

In general, multi-file changes and configuration-dependent issues perform poorly across all the embedding methods explored. 

Comparing the Semantic against Structure+Semantic embedders, which also rely on static pattern-matching rules, reveals a weakness in the hybrid representations for concurrency detection (CWE-362). 
For this type of vulnerability, the structural pipeline relies on regular expressions (\texttt{RE\_LOCK} and \texttt{RE\_UNLOCK}) targeting standard synchronization primitives (e.g., \texttt{mutex\_lock}, \texttt{spin\_lock}, \texttt{rtnl\_lock}). 
However, when codebases use custom thread-safety primitives (such as \texttt{ip\_setup\_cork()}), the race-condition indicator group remains empty.
The remaining feature groups of the pattern embedding are unrelated vulnerability classes (Use-After-Free, Null Pointer Dereference, unchecked returns, array bounds, uninitialized variables, and alloc/free misallocations). 
As a result, the structural vector becomes near-constant noise. 
As the Structure+Semantic model concatenates the structural pattern vector with the CodeBERT embedding and then applies PCA, the semantic signal is then diluted, leading to incorrect retrieval with this embedder.  
This happens, for example, in domain-specific kernel socket handling (CVE-2012-3552) or non-standard ioctl lock routines (CVE-2021-32686, CVE-2020-12652).

These errors occur because these cases use domain-specific identifiers that are not directly related to kernel locking primitives misuse and therefore cannot be matched by the vulnerability flow rules.

Despite these limitations, graph topological kernels demonstrate advantages over pure sequence models when vulnerabilities manifest as local data-dependency pipelines. 
For example, in memory safety instances where structural embeddings capture the missing cleanup node better than token sequences  (e.g., CVE-2016-3841, a Linux IPv6 options UAF), the retrieval accuracy increases from  $\text{MAP} \approx 0.33$ (Semantic) to $\text{MAP} \approx 0.67$ (Structure + Semantic).
Another example is array indexing and bounds checking (CWE-20 and CWE-125), where structural embeddings isolate the CPG subgraph corresponding to the missing bounds check or double-indexing pattern in TensorFlow Lite's array-indexing code(CVE-2020-15211). 
With that, the MAP rises from $\sim0.26$ (Semantic) to $\sim0.73$ (Structure + Semantic).

This pattern was identified using the graph topological kernels that compose the Topological Structure model, namely WL and GIN, even with frozen weights and a shallow architecture.

\section{Cross-Dataset Comparison: AutoPatch vs.\ CVEFixes}

When comparing embedder rankings across datasets, distinct patterns emerge.
On AutoPatch, the topological embedder dominates with 89\% hit@1, while on CVEFixes (Section~\ref{sec:cvefixes-retrieval}), Semantic+Similarity achieves 65.17\% overall CWE accuracy while Topological Structure collapses to 23.60\%.
Possible justifications for this are:

\begin{enumerate}
  \item Even though AutoPatch is primarily built from a crawler on real repositories, it is mostly composed of synthetically augmented code with controlled variations, probably highly preserving core graph topology.
    Whereas CVEFixes contains real-world multi-file patches with few interventions to adapt the format to the dataset storage structure, containing domain-specific identifiers that CodeBERT's vocabulary captures.
  \item CVEFixes vulnerabilities demand greater expertise; for example, the race conditions (CWE-362) often involve domain-specific locking primitives (e.g., \texttt{ip\_setup\_cork}) that the regex-based pattern embedder cannot match.
        On the other hand, AutoPatch locking patterns use standard primitives (\texttt{mutex\_lock}, \texttt{spin\_lock}) more commonly found in codebases, making them more generalizable and easier to identify and patch.
  \item By construction, AutoPatch queries draw from structurally similar augmentations of the same CVE, whereas CVEFixes embedders must emerge patterns that distinguish queries among different vulnerability instances, a harder task.
\end{enumerate}

This indicates that the choice of embedder architecture may depend on the pipeline application context, since no single approach dominates across all vulnerability retrieval scenarios.
The general interpretation of the results is that topological embeddings excel when the core code structure is preserved, whereas semantic embeddings are necessary when vulnerability patterns require domain-specific vocabulary.

% Strong retrieval can enable better downstream patch generation, but evaluating their success reveals a blind spot in standard evaluation metrics. 
% As already mentioned earlier in the chapter, the use of surface-level string and edit-distance metrics—such as BLEU-4, BERTScore F1, and Hunk F1—often creates a false sense of repair quality.
% On the other hand, semantically grounded models may show slight drops in surface-level lexical precision, but they successfully resolve up to nearly 57\% of CVEs and 63\% of CWEs by generating functionally correct fixes.


Qualitative analysis of the generated patches further illustrates the limitations of surface-level evaluations. For example, for  CVE-2020-15211 (CWE-787), the Semantic+Structure pipeline retrieved a CVE-2020-35538 (CWE-476) snippet; therefore, a mismatch. On top of that, the pipeline powered by the GPT-5.3 model generated a patch addressing another CVE, namely CVE-2021-37637, a shape-alignment validation issue. 
To do that, the patch used \texttt{MatchingFlatSize(GetTensorShape(input)} and \texttt{GetTensorShape(output))} to compute the common flat dimensions shared by both tensors, enforcing a dimension match in both production and debug modes. 
Besides these changes, the patch also switched from unbounded pointer arithmetic (\texttt{in++}, \texttt{out++}) to array index lookup bounded by \texttt{flat\_size}:

\begin{lightcpp}
for (int i = 0; i < flat_size; ++i) {
    out[i] = std::min(std::max(0.f, in[i]), 6.f);
}
\end{lightcpp}

This case shows that even though the retriever supplies the patcher agent with a similar CVE's code, a vulnerability patch, vulnerability metadata, a patch CoT, and the root cause (patch-analysis memory), the model can still generate a patch for a different vulnerability than the one queried. 
To support that this is not an isolated case, a similar behavior was found in another test set entry, 
% with (\#78), 
where the CVE and CWE were correctly retrieved according to the dataset, but the actual fix generated by the LLM consisted of replacing \texttt{GetInput}, \texttt{GetOutput}, and \texttt{GetVariableInput} with their \texttt{*Safe} equivalents and guarding them with \texttt{TF\_LITE\_ENSURE\_OK}, even though it had correctly identified that \texttt{bw\_output} retrieval based on the \texttt{merge\_outputs} flag. However, this pattern is related to CVE-2021-29532, a Null Pointer Dereference (CWE-476) that results in a segmentation fault and a Denial of Service (DoS) crash when \texttt{GetInput} returns a \texttt{nullptr} and it's dereferenced. Nevertheless, in its reasoning, the model targets the resolved issue but claims that the retrieved CWE passed as input is the one being addressed. See the justification below: 

\begin{quote}
\textit{Applied the CVE-2020-15211 fix pattern by replacing unchecked tensor accessors with safe accessors that validate index/range and return status, preventing invalid tensor pointer dereference and subsequent out-of-bounds memory writes. Specifically: in Prepare and Eval, replaced GetInput/GetOutput/GetVariableInput with GetInputSafe/GetOutputSafe/GetVariableInputSafe plus TF\_LITE\_ENSURE\_OK checks, and guarded optional bw\_output retrieval when merge\_outputs is false. This is a minimal targeted hardening consistent with the known upstream fix style for this CVE/CWE class.}
\end{quote}

This justification is factually incorrect, since it associates the CWE-476 fix with the CWE-787 stated in the input prompt. 
This mismatch likely occurs because the files were passed separately and stripped of their broader repository context. Therefore, the model lacks the grounding to patch the CWE-787 vulnerability and falls back on its memorized 2021 code structure with the prompt's 2020 metadata.

This has two downstream consequences. In an automated pipeline, having an LLM that generates technically sound patches but hallucinates justifications erodes engineers' trust. Possibly leading them to apply manual review to evaluate the LLM patch and its justification. Furthermore, if the team decides to increase pipeline robustness by attempting more complex prompting, it will increase token usage and inference costs, thereby degrading the patching agent's economic viability.
% This may indicate that the prompt context override the model's latent factual knowledge of vulnerability classifications.

Solutions to these issues could be explored by using CPGs from the retrieval pipeline to represent vulnerabilities mathematically rather than linguistically, anchoring the model to the actual data flow rather than to a prompt.

Even though the pipeline uses different steps to generate a patch and evaluate its alignment with the prompt, it seems that decoupled, agentic workflows are required to enforce correctness.

A possible architecture could consist of a "Generator" agent that proposes a fix based on the retrieved context, while a separate "Reviewer" evaluates the patch. The Reviewer agent can compare the CPG of the generated patch against known secure topologies. This separation of concerns can improve the chances that the generated patch resolves the actual issue.


\subsection*{Functional Validity and Execution Stability}

The trade-off between surface-level accuracy and functional accuracy extends further. As seen in Table \ref{tab:llmjudge_codex53}, the sequential CodeBERT model generates the highest overall rate of functionally valid patches (36.0\%), closely followed by the Topological Structure model pipeline (32.0\%).
However, despite topological features producing syntactically stable code with the lowest runtime error rate (4.0\%), they suffer from the highest invalid patch rate (64.0\%). That is, even though the code runs, it remains vulnerable.

Moreover, the effectiveness of specific embeddings varies heavily by bug type. Explicit data-flow paths in the pattern model yield the highest valid patch rates for concurrency issues (CWE-362), whereas the sequence model excels at localized control-flow fixes.

\subsection*{The C vs. C++ Language Gap}

Performance differs substantially between C and C++, regardless of the chosen embedding strategy.
Across all generation variants, Hunk F1, which measures localized edit precision, drops from approximately 0.93–0.95 in C down to 0.21–0.36 in C++. 
Semantic vector alignment suffers a similar degradation.

\subsection{Patching Powered by GPT-4o and DeepSeek-V4-Flash}

To evaluate the generalizability of the agentic repair architectures, the experiments were also run with GPT-4o and DeepSeek-V4-Flash. The results demonstrate that while the challenges of automated program repair remain, the optimal pipeline configuration is sensitive to the underlying model's reasoning mechanics and its susceptibility to external context.

% \subsubsection{GPT-4o: The Retrieval Distraction Paradox}

Some results for GPT-4o (Table \ref{tab:cwe_comparison_gpt4o}) follow the patterns seen at the Codex-5.3 results. At the lexical level, integrating the Tool Calling framework yields significant improvements over the prompt-only baseline. Prompt-only BERTScore and ROUGE-L scores generally hover in the 0.10–0.43 range, whereas Tool Calling variants elevate these to 0.60–0.99. Vulnerability-specific difficulties also remain static, for example, CWE-787 (Out-of-bounds Write) consistently breaks hunk alignment across all configurations (Hunk $\text{F}_1$ of 0.01--0.13), reinforcing that failures on CWE-787 are probably intrinsic to the complexity of the required memory-management patches rather than a model-specific limitation. Thus, even without being expressly trained for code tasks, its capability of using tools is enough for performance improvement.

However, analyzing the LLM Judge functional validity (Table \ref{tab:llmjudge_gpt4o}) reveals a difference in how GPT-4o handles RAG compared to Codex. For Codex-5.3, RAG pipelines maintained or slightly boosted functional validity. For GPT-4o, applying agentic tooling \textit{without} retrieval yielded the highest functional validity (20 valid patches out of 77 evaluated, or 58 successfully generated). Yet, introducing retrieval (Semantic and Semantic+Structure) degraded performance, dropping the number of valid patches to just 6 and 4, respectively, performing worse than the prompt-only baseline (13 valid).

This probably happens because GPT-4o is optimized for instruction-following and context adherence. When the Semantic or Structure retrievers supply a vulnerability blueprint that is structurally similar but semantically distinct from the target (e.g., retrieving a CWE-476 null-pointer fix for a CWE-787 out-of-bounds write), GPT-4o attempts to force-fit the retrieved solution into the target codebase. Instead of relying on its strong internal priors to independently analyze the target code using its tools, it becomes anchored to the retrieved context, propagating the retriever's slight inaccuracies into catastrophic downstream patch failures. 

GPT-4o presents competitive performance when considering tool calling and Structure. For example, in CWE-416, the Tool Calling (without retrieval) achieves a 0.9791 Hunk $\text{F}_1$, which is actually better than the Codex-5.3 table's maximum of 0.9337. 
Prompt-only performs badly regardless of the model. This suggests that complex code repair requires iterative tool use. The low performance on the Topological Structure indicates that GPT-5.3-Codex recovers from retrieval errors, whereas with GPT-4o, despite the available tools, performance actually suffers.

Overall, the underlying patterns of the task remain identical. For simplicity, one should prioritize Tool Calling w/o retrieval and avoid Patching with prompting without tools. Might also watch for failures for specific vulnerabilities, such as CWE-787, that break hunk alignment. If going for a less powerful model than GPT-5.3-Codex, as exemplified by GPT-4o, one might expect some drop in performance.

% \subsubsection{Language-Specific Vulnerabilities: C vs. C++}

This context-anchoring effect is more pronounced when disaggregating performance by programming language. As observed in the C and C++ language splits, C++ introduces layers that procedural C code lacks, such as abstraction (classes, templates, smart pointers), and polymorphism. Even with a higher retrieval similarity, patch success metrics are lower for C++ cases.

This additional complexity yields a significant drop in lexical alignment across all models when a pipeline attempts to patch C++ repositories. In C, vulnerabilities are often highly localized (e.g., a missing bounds check in a single function), allowing Tool Calling to easily navigate and patch the isolated control flow. 
In C++, a vulnerability might stem from an inherited method or an improperly instantiated template. 
When GPT-4o is provided with topological RAG context for C++, dense object-oriented graphs seem to further degrade retrieval performance and, consequently, generation. The model correctly uses tools to navigate the C++ headers, but if the retrieved RAG context misaligns the complex C++ object lifecycle, the model may generate patches that are syntactically valid (compilable C++) but functionally bypass the vulnerable patching logic entirely. The wrong context causes 28 parse errors, which indicates that the LLM either failed to generate a patch, generated output that couldn't be parsed into valid code, or produced malformed/incomplete responses. In summary, for complex object-oriented vulnerabilities, relying solely on Tool Calling to trace the actual execution path is far more reliable than injecting pre-computed topological structures.

\subsubsection{DeepSeek-V4-Flash: Breaking the Prior Ceiling}

The patching performance of the DeepSeek-V4-Flash model (Tables \ref{tab:patch_similarity_by_cwe_deepseek} and \ref{tab:deepseek_judge_summary}) presents a different dynamic, exemplifying the behavioral differences between proprietary frontier models and more constrained open-weight models. 

Unlike the sharp contrasts seen in GPT-4o, DeepSeek's baseline prompt-only generation achieves a 21.7\% functional validity rate (18 valid out of 83 evaluated), performing on par with its Tool Calling without retrieval pipeline (19 out of 89, or 21.3\%). This suggests that the model's internal reasoning capacity has hit a ceiling, and that giving it tools does not readily improve its ability to synthesize a security fix if it lacks the deep internal priors of a model like Codex or GPT-4o.

Unlike GPT-4o, which collapsed under RAG, equipping DeepSeek with retrieval contexts significantly elevates its performance. The Semantic+Structure and Semantic retrieval methods yield 24 and 23 valid patches, respectively (pushing validity rates to approximately 27.0\% and 25.8\%). Because DeepSeek seems to have weaker memorization of CVEs, it depends on the retrieved context rather than being hurt by it. The retrieved examples provide the necessary semantic trajectory that the model cannot generate zero-shot. This demonstrates that for open-weight models, enriching the context via RAG potentially can break the performance ceiling of the model's native generation capabilities.

% TODO: add citation
Nevertheless, DeepSeek shares the common failure mode of confident hallucination. Despite the improved validity under RAG, the model still generates a vast number of syntactically flawless patches that fail the functional test. The Topological Structure strategy highlights this issue: it resulted in only 6 valid patches (Table \ref{tab:deepseek_judge_summary}). When the retriever supplies poor or purely structural context without semantic grounding, DeepSeek mimics the syntax perfectly but fails to grasp the root cause, compounding the retriever's error rather than correcting it.

\paragraph{GPT-4o.} Once again, the tool-calling pipeline with retrieval has the highest costs, \$0.24--0.26 per entry on average. This indicates that the agentic interaction pattern is the main cost reason, even though the retrieval context itself probably contributes to the costs, since the prompt tokens used in each run add up to millions.

\paragraph{DeepSeek-V4-Flash.} As expected, DeepSeek offers the most cost-effective option with an average of \$0.022--0.024 per entry across all configurations of Agent with tools and retrieval. The model baseline costs only \$0.003 per entry. However, as discussed in Table~\ref{tab:patch_analysis_summary_deepseek}, the DeepSeek generation pipeline experienced output formatting issues that limited the patch generation rate. Therefore, the pipeline might include fallbacks and Human-in-the-Loop verifications if this model is deployed in production. The DeepSeek performance is an example that raw cost efficiency must be weighed against functional reliability.

\section{Generation: AutoPatch Dataset}

The AutoPatch dataset presents a simpler patch-generation task than CVEFixes, as vulnerabilities are generally limited to single functions and involve localized, few-line repairs. This reduced complexity results in higher performance and allows for a cleaner evaluation of the patching pipeline's effectiveness.


\subsection{GPT-5.3-Codex}

Table~\ref{tab:autopatch_overall_pipeline_performance_gpt_codex} summarizes the overall pipeline performance for GPT-5.3-Codex. All three retrieval variants achieve high completion rates (88 - 100\%) and strong LLM Judge validity (70 - 85\%). The Topology retrieval strategy achieves the highest completion rate (100\%), though the lowest Judge validity (85.3\%), followed by Semantic at 96\% completion and a higher validity of 82.7\%. 
The Semantic+Structure  variant, despite lower completion (90\%), achieves 82.7\% validity, the highest in this experiment. Token-based metrics BLEU-4 and ROUGE-L are very similar across these variants ($\approx$0.83 and $\approx$0.90, respectively), indicating that when patches are correctly generated for this dataset, they are textually similar to ground truth regardless of the retrieval strategy.

This statistical equivalence, combined with the high Judge validity rates, suggests that for localized single-function fixes, the choice of retrieval embedding has a low impact on patch quality when using a sufficiently capable model.
The model baseline shows completion rates comparable to those of the retrieval pipelines, even higher than Semantic+Structure, but with lower lexical (BLEU-4 $\approx-13p.p.$ and ROUGE-L F1 $\approx-12p.p.$) and LLM as a Judge validity ($\approx-25p.p.$) metrics. The retrieval performance difference between Topology structure and Semantic+Structure pipelines is accentuated in the patching generation step.
In paired comparisons, Topology retrievals sometimes produce patches with compile errors or misapplied fix patterns.\footnote{For example, CVE-2024-57262: Semantic+Structure retrieved the same CVE and produced a valid patch, whereas Topology retrieved a different CVE and introduced a compile error. Similar issues occurred with CVE-2025-21702 (wrong guard type) and CVE-2025-21801 (double-unlock).} The degradation is concentrated in specific vulnerability classes: NULL Pointer Dereference validity drops from 45.5\% (Semantic+Structure) to 18.2\% (Topology), and Integer Overflow drops from 77.8\% to 66.7\%. Improper Locking remains stable at 92.3\%, suggesting the issue is localized to classes where precise semantic edit patterns matter more than structural similarity. This may indicate that Semantic+Structure retrieves examples with more useful code-level edit semantics, though LLM non-determinism may also contribute. Further investigation is warranted.


\paragraph{Model Comparison.}
Codex achieves 7--29 percentage points higher LLM Judge validity across all retrieval variants compared to GPT-4o. This gap is largest for the Topology retriever (85.3\% vs 56.8\%, $\Delta$=28.5~pp) and smallest for Semantic+Structure (70.3\% vs 63.0\%, $\Delta$=7.3~pp). 
This performance gap suggests that model capability is the dominant factor for localized, single-function vulnerability patches. Additionally, prompt enrichment via the retrieval of similar CWEs yields diminishing returns when the base model is powerful enough.

Conversely, for GPT-4o, the prompt enrichment via retrieval provides a relevant boost. In this case, all three retrieval variants outperform the Tool-only baseline by 6 - 15 percentage points on Judge validity. This indicates that context compensates model limitations by grounding the generation in relevant vulnerability patterns.

\paragraph{Cost Analysis.}
Table~\ref{tab:generation_cost_summary_condensed} summarizes the patch generation costs for AutoPatch. GPT-5.3-Codex is more cost-efficient, with an average of \$0.018-0.020 per patch versus \$0.039--0.042 for GPT-4o with retrieval. The Tool-only GPT-4o baseline has the highest per-entry cost (\$0.224), which may indicate that when there is no retrieval context to guide generation, the model compensates by using more tokens and loops, and, as seen previously, this is not enough to deliver performance. RAG pipelines reduce GPT-4o costs by 5-6$\times$ compared to the no-retrieval baseline while simultaneously improving patch quality. 
Compared to the CVEFixes dataset (Table~\ref{tab:cvefixes_generation_cost_summary}), AutoPatch generation costs are 3 to 6$\times$ lower per entry for equivalent configurations. 
This is probably due to the reduced complexity of the dataset, which consists of single-function and requires localized fixes compared to the multi-file vulnerability patches that require substantially larger context windows and more reasoning steps.

DeepSeek-V4-Flash is by far the cheapest option on AutoPatch, averaging \$0.0035--0.0036 per entry across all three retrieval variants (Sem.+Struc, Semantic, Topology) with tool calling -- roughly 5$\times$ cheaper than GPT-5.3-Codex and 10--12$\times$ cheaper than GPT-4o for the equivalent configuration, despite generating a comparable number of total tokens ($\sim$1M across 75 queries) due to its lower per-token pricing (\$0.19/\$0.51 per 1M input/output tokens). Unlike on CVEFixes, where DeepSeek exhibited severe output-formatting issues (Section~\ref{tab:cvefixes_generation_cost_summary}), on the simpler AutoPatch task it reaches 60.6--71.7\% LLM Judge validity across the three retrieval variants, closer to GPT-4o's range (50--65\%) than to Codex's (70--85\%), which further supports that task complexity, not just raw model capability, drives DeepSeek's reliability gap.

Table~\ref{tab:autopatch_overall_pipeline_performance_deepseek} presents DeepSeek-V4-Flash's tool-calling performance on AutoPatch across the three retrieval variants. \section{Conclusion}

The AutoPatch experiments confirm that model capability is the dominant factor in automated vulnerability patching. GPT-5.3-Codex's LLM Judge validity (70.3--85.3\% across the three retrieval strategies) does not overlap with GPT-4o's (50.0--65.3\%) for any retrieval configuration, and this gap holds regardless of which embedding strategy retrieves the example. DeepSeek-V4-Flash sits between the two (60.6--71.7\%), closer to Codex's floor than to GPT-4o's ceiling, despite being by far the cheapest model evaluated.

No single retrieval strategy dominates consistently across models. Topological Structure achieves the highest Judge validity for both Codex (85.3\%) and DeepSeek (71.7\%), while Semantic retrieval performs best for GPT-4o (65.3\%). The margin between the top two strategies is often narrow relative to the sample size ($N=75$ per configuration) --- DeepSeek's Topological Structure and Semantic+Structure pipelines differ by only 2.0pp (71.7\% vs.\ 69.7\%), which is within the range plausibly attributable to run-to-run variance rather than a systematic effect. The safer reading is that retrieval-strategy choice has a second-order effect on generation quality compared to model capability, consistent with the retrieval-stage finding (Chapter~\ref{chapter:results}, \S\ref{sec:cvefixes-retrieval}) that no embedder wins uniformly across vulnerability classes.

Token-based similarity metrics (BLEU-4, ROUGE-L) plateau across retrieval variants and across models once a patch is successfully generated, and are largely insensitive to the retrieval strategy used to produce it. This is consistent with earlier findings on CVEfixes (\S\ref{sec:cvefixes-retrieval}): lexical similarity to a reference patch is a weak proxy for whether the patch is functionally correct. LLM Judge validity is the metric that actually separates the pipelines in this section, and should be weighted accordingly in any deployment decision.

Retrieval augmentation carries a cost premium rather than a saving. For both Codex and GPT-4o, the retrieval-augmented pipelines cost more per patch than the corresponding no-retrieval baseline (Table~\ref{tab:generation_cost_summary_condensed}) --- for GPT-4o, roughly 1.6--1.75$\times$ the baseline cost. This premium is justified where it buys a validity improvement: GPT-4o's Tool-only baseline (50.0\% Judge valid) is its worst-performing configuration, so all three retrieval variants improve on it despite costing more. Whether the same trade-off holds for DeepSeek could not be confirmed here, since Judge validity was not evaluated for its no-retrieval baseline (Table~\ref{tab:autopatch_overall_pipeline_performance_deepseek}) despite that baseline completing more patches (93.1\%) than any retrieval-augmented pipeline in this chapter. Closing this gap is necessary before claiming that retrieval augmentation benefits weaker models generally, rather than GPT-4o specifically.

DeepSeek-V4-Flash's per-entry cost (\$0.004 with retrieval) is an order of magnitude below Codex (\$0.018--0.020) and GPT-4o (\$0.039--0.042), making it the most cost-efficient option evaluated. However, its Judge validity trails Codex by 13--20pp across matched retrieval strategies, so the cost advantage should be read as a favorable operating point for cost-constrained deployments rather than a like-for-like substitute.

Taken together, these results suggest a practical guideline: for teams with access to a strong proprietary model, retrieval-strategy choice is a secondary tuning decision, and Topological Structure retrieval offers a CPU-only alternative to semantic embeddings with comparable or better outcomes on this dataset. For teams constrained to smaller or cheaper models, the retrieval strategy is not obviously more consequential either -- the larger lever remains base model capability, with retrieval augmentation providing a validity gain in the one case (GPT-4o) where it could be directly measured against a comparable baseline.
