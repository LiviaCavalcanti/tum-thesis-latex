As seen in Table \ref{tab:pca_l2}, $L_2$-normalization is an important component for the retrieval performance, whereas PCA produces a marginal but consistent change across the embedding metrics.
For the Topological Structure embedder, removing PCA results in a slight performance drop from 0.822 to 0.808 in hit@1 (and from 0.860 to 0.844 in MRR), indicating that PCA helps balance the concatenated GIN and WL representations. In contrast, removing $L_2$-normalization causes a severe degradation across all graph-based embedders, reducing Topological Structure hit@1 to 0.0136 and GIN to 0.055, confirming that vector magnitude scaling is essential before computing distance metrics.

To investigate why removing $L_2$-normalization causes such a performance collapse, we analyzed the effective dimensionality of the resulting embedding space. 
Without $L_2$-normalization, raw 768-dimensional CodeBERT output vectors vary in magnitude. 
These scale differences can dominate the distance metrics when the vectors are compressed to 128 dimensions via PCA, masking directional semantics and restricting the embedding space into roughly three effective dimensions (3.13). 
On the other hand, applying $L_2$-normalization forces all vectors onto a unit hypersphere, eliminating magnitude variance so that distance calculations depend strictly on vector orientation. 
This keeps the semantic signal spread across nearly 16 effective dimensions (15.79), thereby preserving CodeBERT's representations and achieving the best retrieval performance (87.7\% hit@1).

While the Semantic embedder achieves the highest overall retrieval performance (Hit@1=0.877), the unsupervised Topological Structure embedder performs competitively (Hit@1=0.822) without relying on pretrained transformer architectures. 
This is especially relevant because topological graphs depend on structural invariants rather than code natural language and can be computed efficiently on CPU-only infrastructure.
Furthermore, structural embedders can be an alternative for rare, legacy, or domain-specific languages where pretrained models lack coverage.
Given that this baseline is completely unsupervised, supervised fine-tuning of lightweight graph neural networks presents a viable, compute-efficient strategy to surpass transformer-based retrieval baselines without requiring dedicated GPU infrastructure.
Therefore, a viable direction for future work is to train GIN as an alternative for out-of-distribution codebases, which can simultaneously explore the emergence of graph representation patterns that better capture vulnerabilities across a larger dimensional region, currently limited to  2.19, with PCA, and 6.83, without PCA.

However, domain-level analysis demonstrates distinct architectural strengths across vulnerability types.
For the \textit{Concurrency} category, the Topological embedder reaches perfect accuracy across all queries (100.0\% CVE and CWE hit rates), outperforming the Semantic model (92.3\%). Concurrency flaws—such as race conditions and deadlocks—depend heavily on inter-thread execution order, control-flow branching (CFG), and data dependencies (PDG), which are explicitly captured by Code Property Graphs but blurred in linear token sequences.
    
For \textit{Memory Safety} (78.6\% vs.\ 82.1\% CVE) and \textit{Resource Management} (83.3\% vs.\ 91.7\% CVE), the Semantic model holds the advantage. While pointer lifetime issues like \textit{Use After Free} favor graph topology, localized guard additions (such as null-pointer checks or resource cleanup flags) introduce distinct token-level cues that sequence transformers detect more effectively than global graph structures.
    
Both embedder families achieve identical 77.8\% CVE retrieval accuracy (and 88.9\% CWE accuracy) on \textit{Numeric/Type} vulnerabilities (e.g., integer overflows), demonstrating equivalent capabilities in capturing scalar arithmetic bounds.

The Topological model fails completely on both (0.0\% hit rate), while the Semantic model retrieves one correctly (50.0\%). These results confirm that while sequence-based semantic embedders excel at localized syntax and high-level logic checks, structural graph embedders provide an essential specialized representation for execution- and control-dependent vulnerability patterns.

\section{CVEFixes: Embedder Retrieval Performance}\label{sec:cvefixes-retrieval}
As with the AutoPatch results, the CodeBERT-based retrievers outperform the Topological Structure embedding model. This suggests that for these real-world scenarios, the underlying semantic signal carries more weight than the aggregated code topological structure representations crafted under the settings used in this work.

\paragraph{Semantic + Structure Performance}
For the Semantic + Structure Retriever, Figure~\ref{img:retrieval_boxplots} shows that vulnerability classes such as CWE-190 and CWE-787 exhibit clear, distinct separations with no overlap between the interquartile ranges (IQRs) or whiskers of incorrect and correct matches. However, an exception occurs in CWE-20, where the ranking scores for incorrect retrievals are concentrated at higher values than the correct ones.

For CWE-476, while correct matches score slightly higher on average, their distributions noticeably overlap, lacking a clean separation. CWE-362 demonstrates a similarly fuzzy boundary. While the IQR for errors is mainly in the lower half of the correct ranking score distribution, the 25th percentile (p25) of correct retrievals aligns with the median of incorrect retrievals.

CWE-416 presents a challenging scenario. The incorrect retrievals exhibit a higher IQR, with its upper quartile significantly overlapping the correct score distribution. In practice, this wide variance means the retriever frequently ranks incorrect queries as highly as correct ones. Because the 75th percentile (p75) of the incorrect scores remains below the maximum of the correct distribution, yet still overlaps with its range, establishing a reliable classification threshold without losses is impossible in this case.

\paragraph{Semantic Retriever Performance}
The Semantic Retriever model exhibits a similar trend but with some differences. 
For CWE-362, the incorrect retrievals have a wider IQR and a higher median than the Semantic and Structure model. 
Additionally, the Semantic model shows a broader spread for correct matches in CWE-416 and CWE-476. Generally, the Semantic model tends to assign higher overall ranking scores, which can amplify false positives. 
Despite this, for both Semantic and Structure, and Semantic-only models, the median ranking score for a correct match remains consistently higher than that of an error for the majority of categories.

\paragraph{Topological Structure Model Performance}
In contrast, the Topological Structure retriever suffers from compressed ranking scores.
While Semantic and Structure, and Semantic-only models successfully cluster correct matches in the 0.6 to 1.0 range, the Topological Structure approach condenses almost all scores in between 0.2 and 0.5.

\paragraph{Vulnerability-Specific Challenges}
The semantic models perform particularly well for CWE-190 and CWE-787. In these categories, correct matches cluster at high scores with narrow IQRs, while errors remain isolated as low-scoring distributions. 
This suggests these specific vulnerabilities possess distinct lexical signatures that CodeBERT can capture.

Conversely, the models struggle significantly with other CWEs.
The CWE-362 (Race Conditions) IQR overlap between correct matches and errors indicates the models struggle to differentiate between safe and unsafe concurrent code operations.
Additionally, the Semantic model exhibits a wide IQR for CWE-476 (NULL Pointer Dereference) errors, and its median is close to the correct match median. 
This high volume of high-ranking false positives likely occurs because a vulnerable missing null check appears textually and sequentially identical to safe code in which a null check is unnecessary.

Evaluating retrieval performance across vulnerability classes reveals that structural and semantic embedders exhibit distinct and complementary failure modes depending on whether a weakness is localized to AST subgraphs or distributed across inter-procedural state and synchronization logic.

\paragraph{Localized Structural Invariance and Inter-Procedural Vulnerability Patterns}
Structure + Semantic model achieves good performance in retrieving localized data-flow and bounds-check patterns (CWE-20: Improper Input Validation and CWE-190: Integer Overflow). 
For example, localized input validation and array-indexing guards (CVE-2021-26788, $hit@=0.93$; CVE-2020-15211, $hit@1=0.73$), the structural component captures the vulnerability on AST conditional nodes and local basic-block boundaries. 
Good performance is also observed when the patch involves modifying existing control constructs, such as reordering statement nodes or adjusting conditional predicates in concurrency guards (CWE-362: Race Conditions, e.g., CVE-2011-1768).

On the other hand, non-local semantic weaknesses, where the vulnerability stems from missing synchronization logic rather than existing control-flow nodes (CWE-362), show low performance. 
To illustrate, there are the following instances:
\begin{itemize}
    \item Complex Concurrency and Race Conditions (CWE-362): Multi-threaded race conditions (e.g., double-fetch bugs in kernel ioctls like CVE-2020-12652 or callback destruction races in network stacks like CVE-2021-32686; both $\text{hit@1}=0.0$) depend on inter-procedural execution order and implicit timing invariants. Because AST and static graph embeddings inspect local function boundaries, they cannot capture missing inter-function synchronization mechanisms.
    \item CVE-2021-32686 ($\text{hit@1}=0.0$, $n=1$): A race condition between socket destroy and callback in PJSIP TLS connections.
\end{itemize}

These vulnerabilities depend on execution order and synchronization across functions, which AST- or graph-structural embeddings cannot capture in the current setting. 
A similar case occurs with a Use-After-Free (CWE-416) CVE-2023-38703 ($\text{hit@1}=0.0$, $n=2$), where the issue is caused by a lack of synchronization between the high-level SRTP transport and the lower-level media transport.

Another failure case stems from the lack of access to external configuration flags and runtime state invariants, as seen in (CWE-476) CVE-2020-10739 ($\text{hit@1}=0.0$, $n=3$), where a Null Pointer Exception in Istio/Envoy was triggered under the Telemetry v2 configuration.

Broad refactoring or multi-file architectural changes, such as locking macros or structural realignment in (CWE-476) CVE-2020-35538 and (CWE-362) CVE-2012-3552, also show low performance (hit@1 < 0.5).

In general, multi-file changes and configuration-dependent issues perform poorly across all the embedding methods explored. 

Comparing the Semantic against Structure+Semantic embedders, which also rely on static pattern-matching rules, reveals a weakness in the hybrid representations for concurrency detection (CWE-362). 
For this type of vulnerability, the structural pipeline relies on regular expressions (\texttt{RE\_LOCK} and \texttt{RE\_UNLOCK}) targeting standard synchronization primitives (e.g., \texttt{mutex\_lock}, \texttt{spin\_lock}, \texttt{rtnl\_lock}). 
However, when codebases use custom thread-safety primitives (such as \texttt{ip\_setup\_cork()}), the race-condition indicator group remains empty.
The remaining feature groups of the pattern embedding are unrelated vulnerability classes (Use-After-Free, Null Pointer Dereference, unchecked returns, array bounds, uninitialized variables, and alloc/free misallocations). 
As a result, the structural vector becomes near-constant noise. 
As the Structure+Semantic model concatenates the structural pattern vector with the CodeBERT embedding and then applies PCA, the semantic signal is then diluted, leading to incorrect retrieval with this embedder.  
This happens, for example, in domain-specific kernel socket handling (CVE-2012-3552) or non-standard ioctl lock routines (CVE-2021-32686, CVE-2020-12652).

% Similarly, CVE-2021-326862, an issue in the Linux kernel that allows local users to hold an incorrect lock during the ioctl operation and trigger a race condition, and CVE-2020-1265, a race condition in SSL sockets under heavy TLS loads where the IP socket option handling can lead to denial of service of open-source multimedia communication libraries, are not correctly retrieved. These errors occur because these cases use domain-specific identifiers that are not directly related to kernel locking primitives misuse and therefore cannot be matched by the vulnerability flow rules. 
% As a consequence, the vectors that flag concurrency vulnerabilities remain empty for both evaluated vulnerable functions, following the same error pattern described previously.  

Despite these limitations, graph topological kernels demonstrate advantages over pure sequence models when vulnerabilities manifest as local data-dependency pipelines. 
For example, in memory safety instances where structural embeddings capture the missing cleanup node better than token sequences  (e.g., CVE-2016-3841, a Linux IPv6 options UAF), the retrieval accuracy increases from  $\text{hit@1} \approx 0.33$ (Semantic) to $\text{hit@1} \approx 0.67$ (Structure + Semantic).
Another example is array indexing and bounds checking (CWE-20 and CWE-125), where structural embeddings isolate the CPG subgraph corresponding to the missing bounds check or double-indexing pattern in TensorFlow Lite's array-indexing code(CVE-2020-15211). 
With that, the hit@1 rises from $\sim0.26$ (Semantic) to $\sim0.73$ (Structure + Semantic).


The cases in which the Topological Structure embedder succeeded reveal its potential for vulnerability investigation. 
The Topological Structure embedder successfully identified integer overflow vulnerabilities in dynamic memory functions (e.g., arithmetic in \texttt{realloc}/\texttt{malloc} calls, as seen in Arithmetic Allocation Pipelines (CWE-190, e.g., CVE-2023-36326). 
This happens because the code contains an arithmetic operation node that feeds directly into an allocation call, without an intervening conditional control-flow branch node. A CPG topology encodes this data-dependency pipeline via Control flow, and, optionally, Data Flow Graph, whereas CodeBERT treats it as tokens separated by intermediate code. This pattern was identified using the graph topological kernels that compose the Topological Structure model, namely WL and GIN, even with frozen weights and a shallow architecture.

\section{Cross-Dataset Comparison: AutoPatch vs.\ CVEFixes}

When comparing embedder rankings across datasets, distinct patterns emerge.
On AutoPatch, the topological embedder dominates with 89\% hit@1, while on CVEFixes (Section~\ref{sec:cvefixes-retrieval}), Semantic+Similarity achieves 65.17\% overall CWE accuracy while Topological Structure collapses to 23.60\%.
Possible justifications for this are:

\begin{enumerate}
  \item Even though AutoPatch is primarily built from a crawler on real repositories, it is mostly composed of synthetically augmented code with controlled variations, probably highly preserving core graph topology.
    Whereas CVEFixes contains real-world multi-file patches with few interventions to adapt the format to the dataset storage structure, containing domain-specific identifiers that CodeBERT's vocabulary captures.
  \item CVEFixes vulnerabilities demand greater expertise; for example, the race conditions (CWE-362) often involve domain-specific locking primitives (e.g., \texttt{ip\_setup\_cork}) that the regex-based pattern embedder cannot match.
        On the other hand, AutoPatch locking patterns use standard primitives (\texttt{mutex\_lock}, \texttt{spin\_lock}) more commonly found in codebases, making them more generalizable and easier to identify and patch.
  \item By construction, AutoPatch queries draw from structurally similar augmentations of the same CVE, whereas CVEFixes embedders must emerge patterns that distinguish queries among different vulnerability instances, a harder task.
\end{enumerate}

This indicates that the choice of embedder architecture may depend on the pipeline application context, since no single approach dominates across all vulnerability retrieval scenarios.
The general interpretation of the results is that topological embeddings excel when the core code structure is preserved, whereas semantic embeddings are necessary when vulnerability patterns require domain-specific vocabulary.

For reference, we also report the Codex-5.3 Baseline, which performs poorly across most of the CWE categories, indicating that prompting alone is insufficient for patching.
A closer examination of the Codex-5.3 Baseline shows that the Hunk F$_1$ score ($0.692$) is seemingly strong overall. 
Breaking down this metric alongside additional metrics collected in the experiments reveals more nuanced behavior. 
While the \texttt{hunk\_removed\_f1} remains high at $0.719$, the \texttt{hunk\_added\_f1} collapses to $0.011$ (notice that these values are not reported in the table for the sake of simplicity). 
This contrast indicates that the baseline model can identify and remove the vulnerable code but almost entirely fails to synthesize the correct repair. 
Because broader metrics evaluate the entire generated output, these low-quality additions significantly reduced the overall patch similarity, yielding a BERTScore F$_1$ of only $0.239$ and a BLEU-4 of $0.127$. 


Continuing the analysis, the tool-calling agent and retrieval-augmented patchers show improved performance compared to the baseline, suggesting that retrieval context and structured prompting enable better patch generation.
Pipelines relying solely on topological data can achieve near-perfect lexical alignment, as indicated by Hunk F1 scores above 0.95 in C code (see Table~\ref{tab:patch_analysis_summary_by_language_codex}), while resolving only 20\% of actual CVEs. 
That happens because their patches successfully reproduce exact syntactic surface edits but fail to resolve the root security vulnerability, as reflected in the low LLM-as-judge valid rate.
Given the similar performance of the tool without retrieval and the Semantic+Structure architecture, the principles of software engineering would prioritize the former architecture, at the cost of lower observability and accountability.

This disconnection between patch generation and its functional validity is an important insight from the LLM Judge evaluation. 
As summarized in Table~\ref{tab:llmjudge_codex53}, the Codex-5.3 Baseline achieved a 100\% generation rate (89/89) without a single execution error, yet yielded only a 21.3\% validity rate (19/89). 
This exposes a dangerous hallucination case in which the model produces syntactically correct patches that pass surface-level checks but fail to resolve the underlying security flaw, probably making these silent failures more problematic than outright generation errors. 
Notably, the integration of agentic tooling alone substantially addresses this gap.
By simply employing structured ReAct prompting and tool access without any external retrieval, the validity rate jumps to 37.6\% (32/85), representing a 76\% relative improvement over the baseline. 
While providing external context via retrieval pipelines yields further gains (reaching up to 42.5\% validity for the Semantic retriever and 35.3\% for Semantic+Structure), these additions are secondary to the initial leap provided by the agentic framework. Ultimately, the data suggests that while retrieved examples help contextualize the vulnerability, equipping the model with the structural tools to reason about the code is the most decisive factor in generating functionally valid security patches.



Analyzing the results by vulnerability type, CWE-787 (Out-of-bounds Write) is the hardest class across all the strategies. Despite having the highest number of small files ($52.41\%$ are $<500$ lines), it yields the lowest Hunk score, close to 0, indicating a low number of valid patches across the three evaluations.
Conversely, CWE-362 (Race Conditions) has 0.0\% files under 500 lines, yet achieves strong retrieval alignment (BERTScore-F1 in the range 0.914-0.974) and up to 33.3\% valid patch rates.
This suggests that patch-generation difficulty is more closely related to the type of semantic vulnerability than to raw code length.


Qualitative analysis of the generated patches further illustrates the limitations of surface-level evaluations. For example, for  CVE-2020-15211 (CWE-787), the Semantic+Structure pipeline retrieved a CVE-2020-35538 (CWE-476) snippet; therefore, a mismatch. On top of that, the pipeline powered by the GPT-5.3 model generated a patch addressing another CVE, namely CVE-2021-37637, a shape-alignment validation issue. 
To do that, the patch used \texttt{MatchingFlatSize(GetTensorShape(input)} and \texttt{GetTensorShape(output))} to compute the common flat dimensions shared by both tensors, enforcing a dimension match in both production and debug modes. 
Besides these changes, the patch also switched from unbounded pointer arithmetic (\texttt{in++}, \texttt{out++}) to array index lookup bounded by \texttt{flat\_size}:

\begin{lightcpp}
for (int i = 0; i < flat_size; ++i) {
    out[i] = std::min(std::max(0.f, in[i]), 6.f);
}
\end{lightcpp}

This case shows that even though the retriever supplies the patcher agent with a similar CVE's code, a vulnerability patch, vulnerability metadata, a patch CoT, and the root cause (patch-analysis memory), the model can still generate a patch for a different vulnerability than the one queried. 
To support that this is not an isolated case, a similar behavior was found in another test set entry, 
% with (\#78), 
where the CVE and CWE were correctly retrieved according to the dataset, but the actual fix generated by the LLM consisted of replacing \texttt{GetInput}, \texttt{GetOutput}, and \texttt{GetVariableInput} with their \texttt{*Safe} equivalents and guarding them with \texttt{TF\_LITE\_ENSURE\_OK}, even though it had correctly identified that \texttt{bw\_output} retrieval based on the \texttt{merge\_outputs} flag. However, this pattern is related to CVE-2021-29532, a Null Pointer Dereference (CWE-476) that results in a segmentation fault and a Denial of Service (DoS) crash when \texttt{GetInput} returns a \texttt{nullptr} and it's dereferenced. Nevertheless, in its reasoning, the model targets the resolved issue but claims that the retrieved CWE passed as input is the one being addressed. See the justification below: 

\begin{quote}
\textit{Applied the CVE-2020-15211 fix pattern by replacing unchecked tensor accessors with safe accessors that validate index/range and return status, preventing invalid tensor pointer dereference and subsequent out-of-bounds memory writes. Specifically: in Prepare and Eval, replaced GetInput/GetOutput/GetVariableInput with GetInputSafe/GetOutputSafe/GetVariableInputSafe plus TF\_LITE\_ENSURE\_OK checks, and guarded optional bw\_output retrieval when merge\_outputs is false. This is a minimal targeted hardening consistent with the known upstream fix style for this CVE/CWE class.}
\end{quote}

This justification is factually incorrect, since it associates the CWE-476 fix with the CWE-787 stated in the input prompt. 
This mismatch likely occurs because the files were passed separately and stripped of their broader repository context. Therefore, the model lacks the grounding to patch the CWE-787 vulnerability and falls back on its memorized 2021 code structure with the prompt's 2020 metadata.

This has two downstream consequences. In an automated pipeline, having an LLM that generates technically sound patches but hallucinates justifications erodes engineers' trust. This may lead them to perform manual review to evaluate the LLM patch and its justification. Furthermore, if the team decides to increase pipeline robustness by attempting more complex prompting, it will increase token usage and inference costs, thereby degrading the patching agent's economic viability.
% This may indicate that the prompt context overrides the model's latent factual knowledge of vulnerability classifications.

Solutions to these issues could be explored by using CPGs from the retrieval pipeline to represent vulnerabilities mathematically rather than linguistically, anchoring the model to the actual data flow rather than to a prompt.

Even though the pipeline uses different steps to generate a patch and evaluate its alignment with the prompt, it seems that decoupled, agentic workflows are required to enforce correctness.

A possible architecture could consist of a "Generator" agent that proposes a fix based on the retrieved context, while a separate "Reviewer" evaluates the patch. The Reviewer agent can compare the CPG of the generated patch against known secure topologies. This separation of concerns can improve the chances that the generated patch resolves the actual issue.

\subsection*{Functional Validity and Execution Stability}

Beyond the aggregate validity rates discussed above, the LLM Judge results (Table~\ref{tab:llmjudge_codex53}) let us separate two distinct failure modes: patches that execute but fail to resolve the vulnerability (\textit{invalid}), and patches that the judge could not evaluate as a coherent fix at all (\textit{error}). This distinction matters because a low validity rate driven by errors points to a different weakness (patch applicability or malformed output) than one driven by invalid-but-executable patches (a semantic/functional failure).

Across all five configurations, LLM as a Judge identifies few errors. The Codex-5.3 baseline, Tool Calling (No Retrieval), and Semantic report zero errors, while Semantic+Structure and Topological Structure each show a small error rate of 2.4\% (2/85). This suggests that the agent reliably produces well-formed patches regardless of the retrieval strategy. The dominant failure mode, however, is semantic.

Analyzing the validity rate, Semantic performs best at 42.5\% (37/87), followed by Tool Calling (No Retrieval) at 37.6\% (32/85), Semantic+Structure and Topological Structure tied at 35.3\% (30/85), and the Codex-5.3 baseline trailing at 21.3\% (19/89). Semantic achieves the highest validity rate, with a zero error rate, making it the recommended choice based on this experimental data.

The baseline's zero error rate does not indicate execution stability. As shown earlier, its high \texttt{hunk\_removed\_f1} alongside a near-collapsed \texttt{hunk\_added\_f1} indicates the model frequently deletes the vulnerable code without contributing a replacement, resulting in a well-formed but functionally empty edit. Its high invalid rate (78.7\%, 70/89) is therefore due to omission, unlike the invalid patches produced by the retrieval-augmented pipelines, which attempt full repair but sometimes fail to resolve the actual vulnerability.

\subsection{Patch Powered by GPT-4o}

To evaluate the generalizability of the agentic repair architectures, the experiments were also run with GPT-4o and DeepSeek-V4-Flash. The results demonstrate that while the challenges of automated program repair remain, the optimal pipeline configuration is sensitive to the underlying model's reasoning mechanics and its susceptibility to external context.

Some results for GPT-4o (Table \ref{tab:cwe_comparison_gpt4o}) follow the patterns seen at the Codex-5.3 results. At the lexical level, integrating the Tool Calling framework yields significant improvements over the prompt-only baseline. Prompt-only BERTScore and ROUGE-L scores generally hover in the 0.10–0.43 range, whereas Tool Calling variants elevate these to 0.60–0.99. Vulnerability-specific difficulties also remain static, for example, CWE-787 (Out-of-bounds Write) consistently breaks hunk alignment across all configurations (Hunk $\text{F}_1$ of 0.01--0.13), reinforcing that failures on CWE-787 are probably intrinsic to the complexity of the required memory-management patches rather than a model-specific limitation. Thus, even without being expressly trained for code tasks, its ability to use tools is sufficient for performance improvement.

This probably happens because GPT-4o is optimized for instruction-following and context adherence. When the Semantic or Structure retrievers supply a vulnerability blueprint that is structurally similar but semantically distinct from the target (e.g., retrieving a CWE-476 null-pointer fix for a CWE-787 out-of-bounds write), GPT-4o attempts to force-fit the retrieved solution into the target codebase. Instead of relying on its strong internal priors to independently analyze the target code using its tools, it becomes anchored to the retrieved context, propagating the retriever's slight inaccuracies into catastrophic downstream patch failures. 

GPT-4o performs worse than Codex-5.3. Considering tool calling and Structure, for example, in CWE-416, the Tool Calling (without retrieval) achieves a 0.791 Hunk $\text{F}_1$, which underperforms the Codex-5.3 table's maximum of 0.934. 
Prompt-only performs badly regardless of the model. This suggests that complex code repair requires iterative tool use. The low performance on the Topological Structure indicates that GPT-5.3-Codex recovers from retrieval errors, whereas with GPT-4o, despite the available tools, performance actually suffers.

Overall, the underlying patterns of the task remain identical. For simplicity, one should prioritize Tool Calling w/o retrieval and avoid Patching with prompting without tools. Might also watch for failures for specific vulnerabilities, such as CWE-787, that break hunk alignment. If going for a less powerful model than GPT-5.3-Codex, as exemplified by GPT-4o, one might expect some drop in performance.

Unlike the sharp contrasts seen in GPT-4o, DeepSeek's baseline prompt-only generation achieves a 20.2\% functional validity rate, performing on par with its Tool Calling without a retrieval pipeline. This suggests that the model's internal reasoning capacity has hit a ceiling, and that giving it tools does not readily improve its ability to synthesize a security fix if it lacks the deep internal priors of a model like Codex or GPT-4o.

Unlike GPT-4o, which collapsed under RAG, DeepSeek, when equipped with retrieval contexts, significantly improves its performance. The Semantic+Structure and Semantic retrieval methods yield 35 and 32 valid patches, respectively (pushing validity rates to approximately 39.3\% and 32.6\%). Because DeepSeek seems to have weaker memorization of CVEs, it depends on the retrieved context rather than being hurt by it. The retrieved examples provide the necessary semantic trajectory that the model cannot generate zero-shot. This demonstrates that, for open-weight models, enriching the context via RAG can potentially improve the performance ceiling of the model's native generation capabilities.

Nevertheless, DeepSeek shares the common failure mode of confident hallucination. When the retriever supplies poor or purely structural context without semantic grounding, DeepSeek mimics the syntax perfectly but fails to grasp the root cause, compounding the retriever's error rather than correcting it.

The AutoPatch dataset presents a simpler patch-generation task than CVEFixes, as vulnerabilities are generally limited to single functions and involve localized, few-line repairs. 
This reduced complexity leads to higher overall performance and enables a cleaner evaluation of how individual retrieval strategies and tool-use mechanisms affect the effectiveness of the automated patching pipeline.

\subsection{Cost Analysis}

Table~\ref{tab:generation_cost_summary_condensed} summarizes patch generation costs for AutoPatch.

GPT-5.3-Codex is the more cost-efficient retrieval augmentation pipeline option of the two proprietary models, averaging \$0.018--0.020 per patch across the three retrieval variants, against \$0.039--0.042 for GPT-4o under the same configurations. The advantage is consistent across variants at 2.1--2.2$\times$ (Sem.+Struc.: \$1.37 vs. \$2.95, 2.15$\times$; Semantic: \$1.46 vs. \$3.18, 2.18$\times$; Topology: \$1.47 vs. \$3.15, 2.14$\times$).

For GPT-4o specifically, costs scale incrementally with pipeline complexity on this simpler dataset. The prompt-only Model baseline is the most economical configuration at \$0.024 per entry (247K prompt tokens). Adding tool calling without retrieval increases the average cost to \$0.032 per entry (a 1.33$\times$ increase, driven by prompt expansion to 445K tokens), while adding retrieval augmentation further raises costs to \$0.039--0.042 per entry (a 1.2--1.5$\times$ increase over tool calling alone, or 1.6--2.0$\times$ over the untooled baseline). Unlike the complex CVEFixes setting, where tool-calling with context expanded rapidly increased the costs, AutoPatch displays a predictable, additive cost progression bounded by a single-function scope.

DeepSeek remains the most economical option, averaging \$0.002-0.003 per entry across the three tool-augmented retrieval variants (Sem.+Struc., Semantic, Topology), approximately 8.0$\times$ cheaper than Codex and 17.2$\times$ cheaper than GPT-4o on the same variants, despite generating a substantially higher volume of completion tokens ($\sim$158-162K tokens vs.\ $\sim$51-57K for Codex and GPT-4o).

Comparing AutoPatch to CVEFixes (Table~\ref{tab:cvefixes_generation_cost_summary}), the impact of dataset complexity surfaces. AutoPatch's single-function scope lowers prompt overhead, making patch generation cheaper across all pipeline configurations. Retrieval-augmented tool-calling configurations cluster in a 4.3-6.2$\times$ cost reduction relative to CVEFixes (e.g., Codex Semantic: \$0.099 vs. \$0.019, 5.2$\times$; GPT-4o Semantic: $0.262 vs. $0.042, 6.2$\times$), reflecting the reduced context passed to the agent and required to reason.


Finally, DeepSeek's bottleneck on complex benchmarks, expressed as output-formatting failures on CVEFixes is less pronounced on AutoPatch. Suggesting that simpler scopes keep the model consistently within its reliable generation range. Therefore, while DeepSeek's cost advantage is substantial regardless of complexity, its functional reliability depends on the dataset complexity.

\subsection{Conclusion}

The AutoPatch experiments confirm that model capability is the dominant factor in automated vulnerability patching. GPT-5.3-Codex's LLM Judge validity (75.6-82.7\% across the three retrieval strategies) does not overlap with GPT-4o's (54.7--62.7\%) for any retrieval configuration, and this gap holds regardless of which embedding strategy retrieves the example. DeepSeek-V4-Flash sits between the two (60.0--72.0\%), closer to Codex's floor than to GPT-4o's ceiling, despite being by far the cheapest model evaluated.

No retrieval strategy consistently dominates across the models tested. Topological Structure achieves the highest Judge validity for both Codex (82.7\%) and DeepSeek (72.0\%), while Semantic retrieval performs best with GPT-4o (62.7\%). The difference between the top two strategies is small, considering the sample size $N=75$. These results suggest that the choice of retrieval strategy has a second-order effect on generation quality. In contrast, model capability is of great importance, consistent with the retrieval-stage finding (Chapter~\ref{chapter:results}, \S\ref{sec:cvefixes-retrieval}) that no embedder uniformly wins across vulnerability classes.

Token-based similarity metrics (BLEU-4, ROUGE-L) plateau across retrieval variants and models for successfully generated patches and are indifferent to the retrieval strategy. This, once again, aligns with earlier findings on CVEfixes (\ref{sec:cvefixes-retrieval}), where the evaluation revealed that lexical similarity to a reference patch is a weak proxy for patch functional correctness. LLM Judge validity is considered a reliable metric used to judge the pipelines in this section, and should be considered accordingly in any deployment decision.

Retrieval augmentation adds to the cost, as it increases the input size, and the pipeline has a fixed size of 6 iterations. For both Codex and GPT-4o, the retrieval-augmented pipelines cost more per patch than the corresponding no-retrieval baseline (Table~\ref{tab:generation_cost_summary_condensed}) --- for GPT-4o, roughly 1.64--1.77$\times$ the baseline cost, which is justified by the validity improvement in all three retrieval variants. 
DeepSeek Judge Validity presents similar improvement between baseline and retrieval pipeline 1.13- $1.31\times$, even though the validity is, overall, higher than GPT-4o - DeepSeek baseline is $1.52\times$ and Semantic+Structure and Topological retrieval variations $1.27-1.31\times$ better when compared to GPT-4o (Table~\ref{tab:autopatch_overall_pipeline_performance_deepseek}). 
However, in GPT-4o, the addition of tools is sufficient to achieve performance similar to (even higher when comparing against Semantic+Structure) the pipeline with tools and context augmentation, even though it is of $\sim2p.p$. 

DeepSeek-V4-Flash's per-entry cost (\$0.002 with retrieval) is an order of magnitude below Codex (\$0.018-0.020) and GPT-4o (\$0.039--0.042), making it the most cost-efficient option evaluated. However, its Judge validity trails Codex by 15.6-15.2pp across matched retrieval strategies, so the cost advantage should be read as a favorable operating point for cost-constrained deployments rather than a like-for-like substitute.

As a whole, these results suggest that for teams with access to a specialized proprietary model, retrieval-strategy choice is a secondary decision for further improvement; Topological Structure retrieval offers a CPU-only alternative to semantic embeddings with comparable or better outcomes on this dataset. 
For teams constrained to smaller or cheaper models, the retrieval strategy is not absolutely required either, as the larger lever remains base model capability,  with retrieval augmentation providing a validity gain when directly compared against a baseline.

The results seem to confirm what the literature review found: LLMs generate plausible code. But the vulnerability-fix effectiveness is much weaker than its ability to write syntactically correct code. This can lead to a misleading sense of safety. On top of that, adding context to enrich the LLM is not trivial, since in many cases we found it degraded performance compared to introducing the tool without retrieval into the pipeline.  

\paragraph{Synthesis of Architectural and Evaluation Dynamics.}
Beyond direct cost metrics, the experimental findings reveal critical insights into tool dynamics, structural retrieval limits, vulnerability topology, and evaluation metric fidelity in automated program repair. Unassisted tool calling incurs severe token inflation (\$0.224/entry) due to unguided, iterative trial-and-error loops; structure-aware RAG acts as a critical bounding mechanism, constraining the search space over the Code Property Graph (CPG) to reduce generation costs by $5\text{--}6\times$ while simultaneously elevating patch validity. Crucially, the optimal retrieval paradigm depends on the underlying vulnerability topology: localized control- and data-flow flaws (e.g., Memory Safety) achieve maximum validity (96.4\%) under pure topological CPG paths, whereas distributed concurrency issues require high-level semantic context. Furthermore, while lower task complexity allows compact open-weight models like DeepSeek-V4-Flash to bridge the performance gap with proprietary models on single-function patches, combining dense semantic and topological contexts induces a context-overload penalty that reduces completion rates. Finally, the results expose a severe disconnect in standard evaluation metrics: surface lexical scores like BLEU-4 remain artificially high ($>0.85$) on micro-edits (e.g., off-by-one or type-bounds fixes) where a single operator changes, completely masking semantic boundary shifts where BERTScore $F_1$ drops to $\approx 0.35$. This underscores the necessity of coupling lexical and semantic metrics with execution-based functional validity and economic efficiency ($\text{Cost}_{\text{Valid}}$) to reliably benchmark program repair systems.
