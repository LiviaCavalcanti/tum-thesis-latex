\subsection{PCA and L2-normalization Ablation}
To validate the proposed architecture, an ablation study was performed to understand the importance of L2-normalization and PCA layers.
Table \ref{tab:pca_l2} shows that dropping \textit{PCA, and L2} is detrimental across every embedder, collapsing hit@1 to 1.4\% or 0.0\%.
This pipeline failure can be explained by the fact that without L2 normalization, FAISS inner product computes:

  $$\text{score}(q, d) = \mathbf{q} \cdot \mathbf{d} = \|\mathbf{q}\| \, \|\mathbf{d}\| \cos\theta$$

so the score is dominated by the vector norms $\|\mathbf{q}\| \, \|\mathbf{d}\|$, rather than the angular similarity $\cos\theta$ that actually reflects the structural similarity.
The result of this can be seen in Table \ref{tab:l2_similarity}.

This effect is worse for \textbf{GIN}, since its sum-pooling component means larger graphs produce larger-norm vectors, and removing the normalization, the retriever just ranks by graph size. \textbf{Combined} shows the same failure, since it inherits GIN's unnormalized scale in the concatenation. GIN explodes from 0.99 with L2 to 260{,}029 without. Whereas, Topological Structurereaches 416{,}081

Therefore, L2 normalization is validated as part of the pipeline.

Analyzing the ranking score distribution per retriever reveals that retrieval difficulty varies significantly across Common Weakness Enumerations (CWEs), with each model demonstrating specific categorical strengths. % TODO: link this with the description to be done in the data section 
Overall, the CodeBERT-based retrievers outperform the Topological Structure embedding model. This suggests that for these real-world scenarios, the underlying semantic signal carries more weight than the aggregated code topological structure representations crafted under the settings used in this work.

\paragraph{Semantic + Structure Performance}
For the Semantic + Structure Retriever, Figure~\ref{img:retrieval_boxplots} shows that vulnerability classes such as CWE-190 and CWE-787 exhibit clear, distinct separations with no overlap between the interquartile ranges (IQRs) or whiskers of incorrect and correct matches. However, an exception occurs in CWE-20, where the ranking scores for incorrect retrievals are concentrated at higher values than the correct ones.

For CWE-476, while correct matches score slightly higher on average, their distributions noticeably overlap, lacking a clean separation. CWE-362 demonstrates a similarly fuzzy boundary. While the IQR for errors is mainly in the lower half of the correct ranking score distribution, the 25th percentile (p25) of correct retrievals aligns with the median of incorrect retrievals.

CWE-416 presents a challenging scenario. The incorrect retrievals exhibit a higher IQR, with its upper quartile significantly overlapping the correct score distribution. In practice, this wide variance means the retriever frequently ranks incorrect queries as highly as correct ones. Because the 75th percentile (p75) of the incorrect scores remains below the maximum of the correct distribution, yet still overlaps with its range, establishing a reliable classification threshold without losses is impossible in this case.

\paragraph{Semantic Retriever Performance}
The Semantic Retriever model exhibits a similar trend but with some differences. 
For CWE-362, the incorrect retrievals have a wider IQR and a higher median than the Semantic and Structure model. 
Additionally, the Semantic model shows a broader spread for correct matches in CWE-416 and CWE-476. Generally, the Semantic model tends to assign higher overall ranking scores, which can amplify false positives. 
Despite this, for both Semantic and Structure, and Semantic-only models, the median ranking score for a correct match remains consistently higher than that of an error for the majority of categories.

\paragraph{Topological Structure Model Performance}
In contrast, the Topological Structure retriever suffers from compressed ranking scores.
While Semantic and Structure, and Semantic-only models successfully cluster correct matches in the 0.6 to 1.0 range, the Topological Structure approach condenses almost all scores in between 0.2 and 0.5.

\paragraph{Vulnerability-Specific Challenges}
The semantic models perform particularly well for CWE-190 and CWE-787. In these categories, correct matches cluster at high scores with narrow IQRs, while errors remain isolated as low-scoring distributions. 
This suggests these specific vulnerabilities possess distinct lexical signatures that CodeBERT can capture.

Conversely, the models struggle significantly with other CWEs.
The CWE-362 (Race Conditions) IQR overlap between correct matches and errors indicates the models struggle to differentiate between safe and unsafe concurrent code operations.
Additionally, the Semantic model exhibits a wide IQR for CWE-476 (NULL Pointer Dereference) errors, and its median is close to the correct match median. 
This high volume of high-ranking false positives likely occurs because a vulnerable missing null check appears textually and sequentially identical to safe code in which a null check is unnecessary.

\subsection{CVE level analysis}

Structure + Semantic model achieves good performance in retrieving localized data-flow and bounds-check patterns. 
For example, (CWE-20) CVE-2021-26788 ($0.93$) and (CWE-20) CVE-2020-15211 ($0.73$) involve localized input validation and bounds checking (e.g., adding \texttt{isxdigit()} checks or guarding pointers within a single block). 
This good performance is explained by the match code, which is based on AST/CPG structural syntax. 
Good performance is also observed when the patch modifies an existing AST node (e.g., reordering calls or tweaking conditionals, as in (CWE-362) CVE-2011-1768).

On the other hand, non-local semantic bugs and cases where the vulnerability stems from missing synchronization logic rather than existing control-flow nodes (CWE-362) show low performance. 
To illustrate, there are the following instances:
\begin{itemize}
    \item CVE-2020-12652 ($\text{MAP}=0.0$, $n=2$): A double-fetch race condition in the Linux kernel (\texttt{\_\_mptctl\_ioctl}).
    \item CVE-2021-32686 ($\text{MAP}=0.0$, $n=1$): A race condition between socket destroy and callback in PJSIP TLS connections.
\end{itemize}

These vulnerabilities depend on execution order and synchronization across functions, which AST- or graph-structural embeddings cannot capture in the current setting. 
A similar case occurs with a Use-After-Free (CWE-416) CVE-2023-38703 ($\text{MAP}=0.0$, $n=2$), where the issue is caused by a lack of synchronization between the high-level SRTP transport and the lower-level media transport.

Another failure case stems from the lack of access to external configuration flags and runtime state invariants, as seen in (CWE-476) CVE-2020-10739 ($\text{MAP}=0.0$, $n=3$), where a Null Pointer Exception in Istio/Envoy was triggered under the Telemetry v2 configuration.

Broad refactoring or multi-file architectural changes, such as locking macros or structural realignment in (CWE-476) CVE-2020-35538 and (CWE-362) CVE-2012-3552, also show low performance (MAP < 0.5).

In general, multi-file changes and configuration-dependent issues perform poorly across all the embedding methods explored. 

The Semantic model (Figure~\ref{img:codebert_seq_cve_map}) shows better performance than the Structure+Semantic model (Figure~\ref{img:codebert_pattern_cve_map}) on CVE-2012-3552, which is a race condition in Linux kernel IP socket option handling. 
It happens because the Structure+Semantic model relies on regular expressions (\texttt{RE\_LOCK} and \textbf{RE\_UNLOCK}) to catch standard locking calls such as \texttt{mutex\_lock, spin\_lock, down\_read/write, and rtnl\_lock}, which fail when the code uses specific domain identifiers. 
This is the case of CVE-2012-3552, which calls \texttt{ip\_setup\_cork()}, performing unprotected-thread data manipulation that is not included in the regex. 
Therefore, the regex group that signals a race condition remains empty. 
The remaining feature groups of the pattern embedding are unrelated vulnerability classes (Use-After-Free, Null Pointer Dereference, unchecked returns, array bounds, uninitialized variables, and alloc/free misallocations). 
As a result, the structural vector becomes near-constant noise. 
As the Structure+Semantic model concatenates the structural pattern vector with the CodeBERT embedding and then applies PCA, the semantic signal is diluted, leading to incorrect retrieval with this embedder.  

Similarly, CVE-2021-326862, an issue in the Linux kernel that allows local users to hold an incorrect lock during the ioctl operation and trigger a race condition, and CVE-2020-1265, a race condition in SSL sockets under heavy TLS loads where the IP socket option handling can lead to denial of service of open-source multimedia communication libraries, are not correctly retrieved. These errors occur because these cases use domain-specific identifiers that are not directly related to kernel locking primitives misuse and therefore cannot be matched by the vulnerability flow rules. 
As a consequence, the vectors that flag concurrency vulnerabilities remain empty for both evaluated vulnerable functions, following the same error pattern described previously.  

On the other hand, semantics is insufficient for cases like CVE-2016-3841 (a Linux IPv6 options UAF), where structural embeddings capture the missing cleanup node better than token sequences. 
As a consequence, the performance of this CVE retrieval rises from $\sim0.33$ (Semantic) to $\sim0.67$ (Structure + Semantic). 
Another example is CVE-2020-15211, in which structural embeddings isolate the AST subgraph of the missing bounds check or double-indexing pattern in TensorFlow Lite's array-indexing code. 
With that, the MAP rises from $\sim0.26$ (Semantic) to $\sim0.73$ (Structure + Semantic).

The cases in which the Topological Structure embedder succeeded, as shown in Figure~\ref{img:combined_cve_map}, reveal its potential for vulnerability investigation. 
The Topological Structure embedder successfully identified integer overflow vulnerabilities in dynamic memory functions (e.g., arithmetic in \texttt{realloc}/\texttt{malloc} calls, as seen in CVE-2023-36326). 
This happens because the code contains an arithmetic operation node that feeds directly into an allocation call, without an intervening conditional control-flow branch node. A CPG topology encodes this data-dependency pipeline via Control flow, and, optionally, Data Flow Graph, whereas CodeBERT treats it as tokens separated by intermediate code. This pattern was identified using the graph topological kernels that compose the Topological Structure model, namely WL and GIN, even with frozen weights and a shallow architecture.

\section{CVEFixes: Patching Experiments}
Given the patch retrieval performance, an analysis of downstream patch generation is necessary to assess the entire pipeline. To evaluate different LLM-powered architectures, two configurations of the agentic pipeline were compared. They share the same parameters: the model, the retrieved example, the target code, and the dataset split. 

\begin{itemize}
    \item \texttt{single\_turn}: few-shot prompt from the prompt registry (\texttt{single\_turn.py}).
    \item \texttt{tool\_calling}: ReAct prompt framework (\texttt{\_SYSTEM\_PROMPT}) combined with auxiliary reviewing code tools (\texttt{tool\_calling.py}).
\end{itemize}

% TODO: we probably should remove the 
Comparing these two fingerprints per record using surface metrics (\texttt{BLEU, ROUGE, Jaccard}), the analysis shows similar results for both strategies.
However, this is not due to similar patch quality.
Rather, this occurs because the metrics become saturated by outputs dominated by unchanged code.

To gain better insights, the evaluation will also consider the hunk metric.
When analyzing the patch difference of the patches generated by the \texttt{CodeBERT\_seq} retriever pipeline, for example, we can see that the fix regions differ.
Patch hunk metrics demonstrate that the \texttt{tool\_calling} agentic approach outperforms \texttt{single\_turn}, improving \texttt{hunk\_token\_jaccard} from $5\%$ to $15\%$ and increasing \texttt{hunk\_removed\_f1} by $+0.17$.
These results indicate that evaluating prompt variations and control-flow strategies requires patch-isolated metrics to clearly evaluate fix quality.

Similarly, applying the hunk metric evaluation to the Topological Structure retriever pipeline, we observe a high rate of incorrect patches (\texttt{hunk\_added\_f1 $\thickapprox$ 0.02}). 
It occurs because the patches simply reproduce the vulnerable input. 
Analyzing the pipeline a step earlier, the retrieval performance is poor with only a 29\% CWE-match rate. %, which suggests that it is important to have a good retrieval. 
Consequently, even though the agent workflow verifies the correctness of the retrieved CVE for the code snippet under analysis, downstream LLM patch generation cannot easily recover from initial retrieval errors, corroborating the importance of robust (context?) retrieval for effective automated repair.

Strong retrieval directly enables better downstream patch generation, but evaluating this success reveals a blind spot in standard evaluation metrics. 
Surface-level string and edit-distance metrics—such as BLEU-4, BERTScore F1, and Hunk F1—often create a false sense of repair quality.
In contrast, semantically grounded models may show slight drops in surface-level lexical precision, but they successfully resolve up to nearly 57\% of CVEs and 63\% of CWEs by generating functionally correct fixes.


For CVE-2020-15211 (CWE-787), the Semantic \& Structure pipeline retrieved a CVE-2020-35538 (CWE-476) snippet; therefore, a mismatch. On top of that, the GPT-5.3 model generated a patch addressing another CVE, namely CVE-2021-37637, a shape-alignment validation issue. The patch used \texttt{MatchingFlatSize(GetTensorShape(input)} and \texttt{GetTensorShape(output))} to compute the common flat dimensions shared by both tensors, enforcing a dimension match in both production and debug modes. The patch also switched from unbounded pointer arithmetic (\texttt{in++}, \texttt{out++}) to array index lookup bounded by \texttt{flat\_size}:

\begin{lightcpp}
for (int i = 0; i < flat_size; ++i) {
    out[i] = std::min(std::max(0.f, in[i]), 6.f);
}
\end{lightcpp}

It shows that even though the retriever supplies the patcher agent with a similar CVE's code, a vulnerability patch, vulnerability metadata (TODO: correctly describe fix list), a patch CoT, and the root cause (patch-analysis memory), the model can still generate a patch for a different vulnerability than the one queried. 
A similar behavior was found in another test set entry, 
% with (\#78), 
where the CVE and CWE were correctly retrieved according to the dataset, but the actual fix generated by the LLM consisted of replacing \texttt{GetInput}, \texttt{GetOutput}, and \texttt{GetVariableInput} with their \texttt{*Safe} equivalents and guarding them with \texttt{TF\_LITE\_ENSURE\_OK}, even though it had correctly identified that \texttt{bw\_output} retrieval based on the \texttt{merge\_outputs} flag. However, this pattern is related to CVE-2021-29532, a Null Pointer Dereference (CWE-476) that results in a segmentation fault and a Denial of Service (DoS) crash when \texttt{GetInput} returns a \texttt{nullpt} and it's dereferenced. Nevertheless, when submitting its reasoning, the model's own justification illustrates the problem: 

"Applied the CVE-2020-15211 fix pattern by replacing unchecked tensor accessors with safe accessors that validate index/range and return status, preventing invalid tensor pointer dereference and subsequent out-of-bounds memory writes. Specifically: in Prepare and Eval, replaced GetInput/GetOutput/GetVariableInput with GetInputSafe/GetOutputSafe/GetVariableInputSafe plus TF\_LITE\_ENSURE\_OK checks, and guarded optional bw\_output retrieval when merge\_outputs is false. This is a minimal targeted hardening consistent with the known upstream fix style for this CVE/CWE class."

This justification is factually incorrect, since it associates the CWE-476 fix with the CWE-787 stated in the input prompt. 
This mismatch likely occurs because the files were passed separately and stripped of their broader repository context. Therefore, the model lacks the grounding to patch the CWE-787 vulnerability and falls back on its memorized 2021 code structure with the prompt's 2020 metadata.

This has two downstream consequences. In an automated pipeline, having an LLM that generates technically sound patches but hallucinates justifications erodes engineers' trust. They must apply manual review to evaluate the LLM patch and its justification. Furthermore, if the team instead decides to increase pipeline robustness by attempting more complex prompting, it will increase token usage and inference costs, thereby degrading the patching agent's economic viability.
% This may indicate that the prompt context override the model's latent factual knowledge of vulnerability classifications.

Solutions to these issues could be explored by using CPGs from the retrieval pipeline to represent vulnerabilities mathematically rather than linguistically, anchoring the model to the actual data flow rather than to a prompt.

Even though the pipeline uses different steps to generate a patch and evaluate its alignment with the prompt, it seems that decoupled, agentic workflows are required to enforce correctness.

A possible architecture could consist of a "Generator" agent that proposes a fix based on the retrieved context, while a separated "Reviewer" evaluates the patch. The Reviewer agent can compare the CPG of the generated patch against known secure topologies. This separation of concerns can improve the chances that the generated patch resolves the actual issue.


\subsection*{Functional Validity and Execution Stability}

The trade-off between surface-level accuracy and functional accuracy extends further. As seen in Table \ref{tab:llmjudge_codex53}, the sequential CodeBERT model generates the highest overall rate of functionally valid patches (36.0\%), closely followed by the Topological Structure model pipeline (32.0\%).
However, despite topological features producing syntactically stable code with the lowest runtime error rate (4.0\%), they suffer from the highest invalid patch rate (64.0\%). That is, even though the code runs, it remains vulnerable.

Moreover, the effectiveness of specific embeddings varies heavily by bug type. Explicit data-flow paths in the pattern model yield the highest valid patch rates for concurrency issues (CWE-362), whereas the sequence model excels at localized control-flow fixes.

\subsection*{The C vs. C++ Language Gap}

Performance differs substantially between C and C++, regardless of the chosen embedding strategy.
Across all generation variants, Hunk F1, which measures localized edit precision, drops from approximately 0.93–0.95 in C down to 0.21–0.36 in C++. 
Semantic vector alignment suffers a similar degradation.

\subsection{Patch Powered by GPT-4o}

The results in Table \ref{tab:cwe_comparison_gpt4o} follow similar patterns to those observed in Table \ref{tab:cwe_comparison_all_methods}. Tool Calling Agent, both with and without retrieval for CodeBERT variations, outperformed the prompt-only GPT-4o baseline. Comparing token-level metrics, prompt-only BERTScore/ROUGE scores hover in the 0.10–0.35 range, while Tool Calling raises them to 0.60–0.99.

Similar to Codex, CWE-787 (Out-of-Bound) vulnerability shows the weakest performance. While BERTScore and ROUGE-L remain stable, Hunk $\text{F}_1$ collapses to almost zero across all methods (0.01–0.18). This suggests that the failures on CWE-787 are intrinsic to the task difficulty due to factors like the dataset sample or the complexity of the patch required for that specific CWE.

Conversely, most Tool Calling methods excel at CWE-362 (Race Conditions), achieving ~0.98–0.99.2, similar to scores seen previously (~0.97–0.99). On the other hand, while the individual Tool Calling methods perform very similarly in Table \ref{tab:cwe_comparison_gpt4o}, the \texttt{Combined} retrieval pipeline showed a drop in performance. For example, in CWE-416, it scored a 0.9369 BERTScore and 0.9691 ROUGE-L, with GPT-5.3-Codex, whereas with GPT-4o it fell to 0.2671 and 0.3390, respectively. Comparatively, it is worse than the Tool Calling (without retrieval) CodeBERT Seq/Pattern Tool Calling patches across almost every single category. 


GPT-4o presents competitive performance when considering tool calling and CodeBERT seq. For example, in CWE-416, the Tool Calling (without retrieval) achieves a 0.9814 Hunk $\text{F}_1$, which is actually better than the Codex-5.3 table's maximum of 0.9337. 
Prompt-only performs badly regardless of the model. This suggests that Complex code repair strictly requires iterative tool use. The Topological Structure low performance here indicates that the GPT-5.3-Codex recovers from the retrieval errors, whereas with GPT-4o, despite the available tools, it actually hurts the performance

Overall, the underlying patterns of the task remain identical. For simplicity, one should prioritize Tool Calling w/o retrieval and avoid Patching with prompting without tools. Might also watch for failures for specific vulnerabilities, such as CWE-787, that break hunk alignment. If going for a less powerful model than GPT-5.3-Codex, as exemplified by GPT-4o, one might expect some drop in performance.

Tables \ref{tab:patch_analysis_summary_deepseek} and \ref{tab:patch_analysis_summary_by_cwe_deepseek} show the patching performance of the DeepSeek-4-Flash model. As previously remarked, they reinforce the need for agentic multi-turn workflows for automated program repair. 

Prompt-only generation fails to produce functionally valid code. Despite achieving token-based evaluation success rates of 28.1\% to 33.7\%, the prompt-only LLM Judge Valid rates hover between 0.0\% and 1.1\%. On the other hand, the multi-turn Tool Calling pipeline powered by  DeepSeek shows higher functional validity. The \textit{CodeBERT Pattern} and \textit{CodeBERT Sequence} retrieval methods achieve valid rates of 27.0\% and 25.8\%, respectively, outperforming baseline Tool Calling without retrieval (21.3\%). This demonstrates that for pipelines powered by less powerful models, such as DeepSeek, enriching the context with the semantic and structural root causes of vulnerabilities via RAG can increase performance. Whereas relying on the model generation capacity may result in syntactically plausible edits being predicted. Nevertheless, it is notable that performance is lower than that of proprietary OpenAI models from previous subsections. Therefore, it reinforces the need for compensation in engineering effort when the pipeline uses open-weight models.  

% Additionally, DeepSeek exhibits a higher iteration overhead compared to Codex and GPT-4o. The model averages 5.2 to 5.5 turns per patch generation, suggesting a more exploratory and error-prone reasoning process before converging on a final solution. 

Furthermore, the \textit{Combined} retrieval strategy has the LLM Judge functional validity of 6.7\%. Repeating the behavior observed in GPT-4o, DeepSeek struggles to recover the vulnerability identification errors of the retriever, which composes with the errors of the model itself.

Vulnerability-specific patterns are also reproduced under the DeepSeek experiment. As seen in Table \ref{tab:patch_analysis_summary_by_cwe_deepseek}, Tool Calling with Pattern retrieval achieves 73.3\% syntax success and a 93.3\% verify rate on CWE-787. Yet, high performance does not translate to LLM as a Judge's functional validity for out-of-bounds writes. DeepSeek's performance confirms the overall evaluation that reliable automated vulnerability patching demands agentic, iterative tool use coupled with isolated, targeted retrieval, even though further exploration on the agentic workflow is required to meet reliable performance for production code.

Table~\ref{tab:cvefixes_generation_cost_summary} summarizes the generation costs for the CVEfixes dataset experiments across different models and pipeline configurations. 

\paragraph{GPT-5.3-Codex.} Codex baseline costs \$0.03 per entry, while tool-calling without retrieval averages \$0.06 per entry. The retrieval-augmented tool-calling variants average \$0.08--0.10 per entry. This indicates that the agentic interaction pattern is the main cost reason, even though the retrieval context itself probably contributes to the costs since the prompt tokens used in each run sum up to millions.

\paragraph{DeepSeek-V4-Flash.} As expected, DeepSeek offers the most cost-effective option with an average of \$0.022--0.024 per entry across all configurations of Agent with tools and retrieval. The model baseline costs only \$0.003 per entry. However, as discussed in Section~\ref{tab:cvefixes_overall_patch_generation_summary_deepseek}, the generation pipeline with DeepSeek experienced output formatting issues that limited the patch generation rate. Therefore, the pipeline might include fallbacks and Human-in-the-Loop verifications if this model is deployed in production. The DeepSeek performance is an example that raw cost efficiency must be weighed against functional reliability.

Analyzing the Figure \ref{img:cost_bertscore_cvefixes}, GPT-5.3-Codex presents the highest BERTScore ($\sim0.825$) with the Semantic retrieval pipeline at \$0.075/entry. GPT-4o delivers performance similar to GPT-5.3-Codex but is twice as expensive (\$0.16-0.17/entry). The model baselines are low-cost but low-performing, reinforcing the previously found indication that the patching task requires tooling to succeed. Similarly, the cost of one prompt with the code, represented by the squares, can be even higher than if you use the retriever that filters the context to be passed, even though the cost is not translated into the BERTScore-F1 metric.

\section{Generation: AutoPatch Dataset}

The AutoPatch dataset presents a simpler patch-generation challenge than CVEfixes, as vulnerabilities are generally limited to single functions and involve localized, few-line repairs. This reduced complexity results in higher performance and allows for a cleaner evaluation of the patching pipeline's effectiveness.

\paragraph{Terminology.} Throughout this section, we refer to three retrieval strategies by their embedding characteristics: \textit{Semantic+Structure} (CodeBERT Pattern), which combines semantic code embeddings with structural graph features; \textit{Semantic} (CodeBERT Seq), which uses sequential code embeddings; and \textit{Topology} (Combined), which relies primarily on graph-topological similarity.

\subsection{GPT-5.3-Codex}

Table~\ref{tab:autopatch_overall_pipeline_performance_gpt_codex} summarizes the overall pipeline performance for GPT-5.3-Codex. All three retrieval variants achieve high completion rates (88 - 100\%) and strong LLM Judge validity (70 - 85\%). The \textit{Topology} retrieval strategy achieves the highest completion rate (100\%) and Judge validity (85.3\%), followed by \textit{Semantic}  at 96\% completion and 82.7\% validity. The \textit{Semantic+Structure}  variant, despite lower completion (88\%), still achieves 70.3\% validity. Token-based metrics (BLEU-4, ROUGE-L) are very similar across these variants ($\approx$0.83 and $\approx$0.90, respectively), indicating that when patches are correctly generated for this dataset, they are textually similar to ground truth regardless of the retrieval strategy.

\paragraph{Model Comparison.}
Codex achieves 7--29 percentage points higher LLM Judge validity across all retrieval variants compared to GPT-4o. This gap is largest for the Topology retriever (85.3\% vs 56.8\%, $\Delta$=28.5~pp) and smallest for Semantic+Structure (70.3\% vs 63.0\%, $\Delta$=7.3~pp). 
This performance gap suggests that model capability is the dominant factor for localized, single-function vulnerability patches. Additionally, prompt enrichment via the retrieval of similar CWEs yields diminishing returns when the base model is powerful enough.

Conversely, for GPT-4o, the prompt enrichment via retrieval provides a relevant boost. In this case, all three retrieval variants outperform the Tool-only baseline by 6 - 15 percentage points on Judge validity. This indicates that context compensates model limitations by grounding the generation in relevant vulnerability patterns.

\paragraph{Cost Analysis.}
Table~\ref{tab:generation_cost_summary_condensed} summarizes the patch generation costs for AutoPatch. GPT-5.3-Codex is more cost-efficient, with an average of \$0.018-0.020 per patch versus \$0.039--0.042 for GPT-4o with retrieval. The Tool-only GPT-4o baseline has the highest per-entry cost (\$0.224), which may indicate that when there is no retrieval context to guide generation, the model compensates by using more tokens and loops, and, as seen previously, this is not enough to deliver performance. RAG pipelines reduce GPT-4o costs by 5-6$\times$ compared to the no-retrieval baseline while simultaneously improving patch quality. 
Compared to the CVEfixes dataset (Table~\ref{tab:cvefixes_generation_cost_summary}), AutoPatch generation costs are 3 to 6$\times$ lower per entry for equivalent configurations. 
This is probably due to the reduced complexity of the dataset, which consists of single-function and requires localized fixes compared to the multi-file vulnerability patches that require substantially larger context windows and more reasoning steps.

\section{conclusion}
the retrieval-augmented pipeline achieves high success rates (70--85\% Judge validity with Codex, 56--65\% with GPT-4o) with AutoPatch dataset. 
The key findings prioritize model capability: GPT-5.3-Codex substantially dominates, outperforming GPT-4o regardless of retrieval strategy. 
Also, when using less capable models, retrieval augmentation is particularly beneficial. 
Regarding the evaluation, token-based metrics (BLEU, ROUGE) can plateau across variants and are vulnerable to data preprocessing, but Judge validity can reveal meaningful evaluation in such cases. 
Finally, the Topology retrieval achieves the best trade-off of completion rate and functional validity for the stronger model, while Semantic+Structure offers the most stable performance for the weaker model.
