\section{AutoPatch}
The AutoPatch dataset contains high-severity CVEs disclosed in 2024 and 2025 and collected from the GitHub Advisory Database, Openwall, and the Chromium issue tracker with a custom crawler.
For each CVE, the entry pairs were augmented using 5 LLMs:  Code Llama (13b-instruct), DeepSeek Coder (v2-lite), DeepSeek-R1 (32b), GPT-4o, and OpenAI o3-mini.
The augmentation strategies used were: "inserting unreachable code fragments, adding random code in comments, varying whitespace and formatting, defining a useless function, and introducing extraneous newline characters".

\subsection{Fix Description Encoding}
 
The AutoPatch dataset is organized into directories where each entry is stored in a folder containing a description JSON (\texttt{db\_entry.json} file=, which includes a field describing the remediation strategy at a symbolic, variable-agnostic level (\texttt{fix\_list}).
The fix description uses symbolic names with variable and function
mappings (e.g., \textit{''add a NULL check before dereferencing the
pointer''}) lets a fixed pattern learned from one example
be transferred to a structurally similar target function. 
With this description, the LLM is expected to use the abstract fix description to apply the required changes to the target using the actual identifiers. 
Section~\ref{chapter:methodology} details how this field is used when constructing prompts for patch generation.

\section{CVEfixes}\label{sec:cvefixes}

CVEfixes\cite{moonen2024cvefixes} is a vulnerability dataset for data-driven security research automatically collected and curated from Common Vulnerabilities and Exposures (CVE) records from the public U.S. National Vulnerability Database (NVD). 
The dataset includes detailed information about the Pull Request CVE resolution, such as the commit-, file-, and method level, as well as the repository- and CVE level.
The general statistics are shown below: 

\begin{itemize}
    \item\textbf{CVEs} 11,873 vulnerabilities
    \item\textbf{commits} 12,107 fix commits
    \item\textbf{files} 51,342 changed files
    \item\textbf{method-change rows} 277,948 rows in the \texttt{method\_change} table
    \item\textbf{CWE types} 272 distinct types
    \item\textbf{projects} 4,249 open-source projects
\end{itemize}

% Origin, Collection method, Composition used
This project uses version v1.0.8, which covers all published CVEs up to 23 July 2024. According to the authors, the projects considered in this dataset include all open-source projects that were reported in CVE records in the NVD in this time frame and had publicly available git repositories. The dataset is stored in a relational database, containing 272 different CWE types across 12107 vulnerability-fixing commits from 4249 open-source projects. The dataset includes the source code before and after changing 51342 files. Each function change is stored as two rows in \texttt{method\_change} (one \texttt{before\_change} snapshot, one after), so the 277,948 raw rows correspond to 138,974 distinct before/after function-pair changes.

\subsection{Final Evaluation Corpus Construction}

The final dataset was split into an index set for the retrieval knowledge base and a query set for testing at an 80/20 ratio per CWE category. 

To maintain an equal, uniform distribution across categories, both the index and query (test) datasets are balanced across the six Common Weakness Enumerations: CWE-362, CWE-476, CWE-416, CWE-20, CWE-190, and CWE-787. 
Each of the six CWE types accounts for exactly 16.7\% of the data within every split, comprising 60 records per category in the index ($N = 360$ total) and 15 records per category in the query dataset ($N = 90$ total). Across the overall dataset of 450 items, each CWE category contributes precisely 75 records (16.7\%), ensuring that no single vulnerability class biases retrieval indexing or evaluation performance.

\subsection{Complexity Description}
\paragraph{CWE-787: Out-of-Bounds Write :} occurs when a program writes data beyond the end or before the beginning of an intended memory buffer. 
This flaw can lead to memory corruption, process crashes, or the execution of arbitrary code. 
The testing sample consists of C++ implementation files from the TensorFlow and TensorFlow Lite runtime/kernel libraries, focusing on kernel operations, tensor management, custom audio operators, and model-building infrastructure.

\paragraph{CWE-362: Concurrent Execution using Shared Resource with Improper Synchronization / Race Condition :}Occurs when a program performs two or more operations concurrently, and the outcome depends on the non-deterministic sequence of execution. If shared resources (memory spaces, sockets, files) are accessed without proper synchronization primitives, concurrent threads can manipulate memory unexpectedly, leading to privilege escalation, data corruption, or crashes.
The CWE-362 sample is predominantly composed of lower-level C code within the Linux Kernel (network stack \texttt{net/ipv4}, storage systems fs/ext4) and cryptographic/communication libraries (e.g., OpenSSL/SRTP).
Rather than relying on naive global locks, the ground-truth patches exhibit high domain-specific synchronization complexity, for example:
Fixes rely on socket-specific concurrency macros (\texttt{lock\_sock}/\texttt{release\_sock}) and kernel-level Read-Copy Update (\texttt{rcu\_dereference}, \texttt{rcu\_assign\_pointer}) primitives to safely manage \texttt{ip\_options} memory across concurrent socket writes.
File System Read-Write Inconsistencies \& Semaphores involve ext4 race conditions between page faults and file truncation (\texttt{fallocate}/\texttt{truncate}), requiring reader-writer semaphores (\texttt{i\_mmap\_sem}) or explicit inconsistency flags instead of adding simple mutexes.
Structural Decoupling \& Flagging is solved either by passing objects directly to eliminate state copies or by enforcing strict synchronization across concurrent SSL resource access paths without basic \texttt{lock}/\texttt{unlock} wrappers.


\paragraph{CWE-20: Improper Input Validation :}
Occurs when an application fails to validate, sanitize, or verify input before processing it, based on expected structural, length, or character-format requirements.
The fix pattern consists of inserting input-character bounds checks (e.g., validating hex strings via \texttt{isxdigit()}) to ensure that user-supplied input strings conform to expected formats before execution.

\paragraph{CWE-190: Integer Overflow or Wraparound :}
Occurs when an arithmetic calculation produces an integer value outside the representable range of the specified data type, typically resulting in undersized buffer allocations.
The fix pattern requires inserting safe integer-arithmetic checks before dynamic memory operations (\texttt{malloc}, \texttt{realloc}) to prevent small, wrapped-integer sizes from being allocated for large data streams.

\paragraph{CWE-416: Use After Free (UAF) :}
Occurs when an application continues to use a memory pointer after it has been explicitly deallocated or freed. 
This can lead to arbitrary code execution, heap corruption, or diversion of execution paths.
The sample contains C/C++ network stack and media-streaming components vulnerabilities, including Linux IPv6 socket lifecycle and SRTP session cleanup. 
The patch consists of resetting dangling pointers to \texttt{nullptr}, managing reference counts, or ensuring that asynchronous destructor routines do not access freed memory blocks.

\paragraph{CWE-476: NULL Pointer Dereference :}
Occurs when a program attempts to read or write memory using a pointer variable that evaluates to \texttt{nullptr}, leading to Denial of Service of the application.
The sample includes media processing frameworks and proxy servers, such as GPAC multimedia handling and Istio/Envoy proxy handling. 
The patches consist of applying explicit null-check guards (\texttt{if (ptr == nullptr) return;}) or safe-access wrappers before accessing the fields.
