\chapter{Methodology}\label{chapter:methodology}

One of the goals of this work is to use historical knowledge from previous fixes to generate fixes for new, structurally similar vulnerable code.

\section*{Architecture}
% content: KB + agentic framework description
This project presents a structure-aware retrieval system that identifies the type of vulnerability in a code snippet and suggests a patch grounded in similar previously seen fixes. 
These previously fixed code snippets are used to build a knowledge base (KB) indexed with embeddings built from the code. This knowledge base is combined with an agentic generation layer that, given the context retrieved, prompts an LLM to produce a candidate patch.

\section*{Data Pipeline}

Following the architecture definition, the data pipeline was implemented in separate layers: Retrieval and Generation.
Besides that, the system can be split into offline retrieval-index construction of the KB, and an online stage in which retrieval occurs independently, before the patch generation.

\paragraph{Offline index construction.} Building the index process consists of:

\begin{itemize}
  \item loading a vulnerable code snippet; 
  \item building a CPG from the code;
  \item embedding the graph;
  \item indexing the resulting embeddings into a vector database (FAISS).
\end{itemize}

\paragraph{Online Query and generation.} At inference time, the pipeline runs the following steps:
\begin{itemize}
  \item transforms the input code snippet into an embedding;
  \item queries the vector database to retrieve similar code, indicating they contain a similar underlying vulnerability;
  \item uses the retrieved entry's data, notably, the patched code, to prompt an LLM to generate a fix for the query vulnerability.
\end{itemize}

In the development phase, retrieval and patch can be assessed on a held-out test set using the automated evaluation script described in ~\ref{section:evaluation}. %TODO: add the section

\section*{Graph Generation}\label{sec:graph-generation}

This work uses Joern to generate the Code Property Graph (CPG) from a code snippet. 
For snippets that are not well-formed C/C++ programs, notably those from AutoPatch, the pipeline first wraps the code with the minimum necessary macros and type definitions (e.g. \ \verb|typedef unsigned int u32|, \verb|#define NULL ((void*)0)|) and writes a parseable source file.

The resulting C/C++ file is compiled into a binary graph representation with the Joern shell command \verb|joern-parse --language newc|, where \verb|newc| is used to handle C\/C++ language constructs and to avoid malformed graphs.  
Then, the compiled graph is exported to GraphML format with the shell command \texttt{joern-export --repr cpg --format graphml}. 
Each export generates a directory tree where each subdirectory contains an \verb|export.xml| file with a subgraph of the full CPG.

The nodes can have different labels (e.g.\ \verb|CALL|, \verb|IDENTIFIER|, \verb|CONTROL_STRUCTURE|), while the edges can belong to one of the following graph representations layered over the same node set: 
Abstract Syntax Tree (AST), Control Flow Graph (CFG), Call Dependency Graph (CDG), and Program Dependency Graph (PDG). % TODO: review the following definitions
\begin{itemize}
    \item AST: syntactic parse structure of the source code.
    \item CFG: possible execution paths through the code (branches, loops).
    \item CDG: control-dependency relationships between statements (which conditionals govern which statements' execution).
    \item PDG: data- and control-dependency edges combined, capturing both what controls a statement's execution and what data it depends on.
\end{itemize}

\section*{Graph Sampling}
Once loaded, the CPG contains the full code file, including the boilerplate added in the graph-generation wrapping pipeline step (Section~\ref{sec:graph-generation}).
Therefore, it is necessary to isolate the subgraph related to the vulnerability from the irrelevant rest of the code. 
For that, a subsample is calculated from the difference between the vulnerable graph and the patched graph, the so-called $G_{\mathrm{vuln}}$. 
By doing so, we expect to be able to generalize the search for the vulnerability, removing the specificities of a given system that are imprinted in the graph.

\paragraph{Bounded slicing}
To include context that may be relevant, a bounded search is performed with the goal of including any relevant settings in which the vulnerability occurs.
The slice is a configurable neighborhood expansion ($n \in \{0,1,2,3\}$ hops). $n=0$ is the original sampled graph, that is, only the directly changed nodes.
    
\paragraph{Semantic difference}
Before performing the sampling, each node needs to be deterministically identifiable to avoid different results depending on runs or randomness resulting from a non-deterministic ID assigned by Joern across runs.
The nodes in the sample are further enriched with semantic labels resulting from the comparison of the two graphs.
Each node of the sample is labeled as either:
\begin{itemize}
  \item Removed node: every node present in $G_\mathrm{orig}$ but absent in the $G_\mathrm{patch}$.
  \item Fix-adjacent node: every node present in $G_\mathrm{orig}$ that is a removed node neighbor.
  \item Edge-changed node: every node attached to an edge which any of the nodes changed between the two graphs. 
\end{itemize}

Besides the labelling, the $G_\mathrm{vuln}$ nodes also received weights. 
\begin{center}
\begin{tabular}{lc}
  \textbf{Label} & \textbf{Weight} \\
  \hline
  \texttt{removed}       & 1.0 \\
  \texttt{fix\_adjacent} & 0.8 \\
  \texttt{edge\_changed} & 0.6 \\
  \texttt{context}       & 0.2 \\
\end{tabular}
\end{center}

These weights are directly proportional to the relation of the node to the vulnerability and will be integrated to the embedders for further prunning.

\subsection*{Embedders}

Two embedding families were evaluated: deterministic embedders, built on heuristics or well-defined mathematical formulations, and semantic embedders, built on pretrained language model of code.
All embedders are \textbf{unsupervised}, that is, no labeled training data required.
By default, each embedder output is an L2-normalized vector with a dimension of 128.
This vector is then passed through the PCA reduction step.

\begin{itemize}

  \item \textbf{NetLSD} (\textit{Network Laplacian Spectral Descriptor}) ~\cite{netlsd}.
  Computes the heat trace of the normalized graph Laplacian across a timescale that aims to get graph expressive representations similar to random walk models.
  It is node permutation-invariant and captures global spectral structure, adapting to scale encoding both local and global features, that is, it is scale-adaptable. 
  It can also compare graphs of different sizes and supports weighted graphs. 
  NetLSD was created to be an alternative to graph edit distance, which is NP-hard to compute exactly. NetLSD comparison is efficiently computable; the calculation can be done in a constant time given precomputed descriptors. 

  \item \textbf{WL} (\textit{Weisfeiler-Lehman Kernel}).
    Implemented via iterative color refinement over node types, followed by weighted sum pooling (\texttt{global\_add\_pool}) and a linear projection. 
    In this work, it was implemented in PyTorch Geometric with no external dependency. 
    % \texttt{diff\_weight} biases pooling toward high-signal nodes.
    WL proceeds in the following iterative fashion: 
    (1) aggregates the labels of nodes and their neighborhoods, 
    and (2) hashes the aggregated labels into unique new node labels.
    As input, it receives  11-class one-hot over CPG node types (METHOD, CALL, IDENTIFIER, etc.) which can be, optionally, enriched with one-hot encoding 5-dimension diff-label and a 1-dimension \texttt{diff\_weight} scalar, resulting in 17 dims per node. The pipeline uses it untrained with the random weights fixed at seed 42.

  \item \textbf{GIN} (\textit{Graph Isomorphism Network}) ~\cite{xu2019gin}
   A message-passing neural Network that evaluates whether two graphs are topologically identical. It is equivalent to the Weisfeiler-Lehman isomorphism test in expressiveness.
   At an algorithm level, it consists of a Graph Neural Network that represents each node by recursively aggregating the neighboring representations. 
    The node representation is updated at each layer \texttt{k} by aggregating the representations of its neighbors via a sum aggregator, followed by an MLP:
    $$h_v^{(k)} = \text{MLP}^{(k)}\!\left((1+\epsilon)\cdot h_v^{(k-1)} + \sum_{u \in \mathcal{N}(v)} h_u^{(k-1)}\right)$$

  Where $\epsilon$ is either a learnable parameter or a fixed scalar (TODO: check what is the case here).
  $h_v^{(0)}$ is initialized from the node features. (TODO: explain network initialization).
  The number of layers is equivalent to the number of neighbor hops that will be encoded by each node.
  This choice is a trade-off between the amount of local structural pattern and the global one.  
  Therefore, it learns to embed the subtree in a low-dimensional space, not only discriminating different structures but also mapping similar embeddings for similar structures and capturing dependencies between graph structures.
  Graph-level embeddings are obtained via dual pooling, concatenating sum pooling and mean pooling outputs. 
  The sum pooling preserves structural size information, while mean pooling makes the normalized representations.
  $$\mathbf{h}_G = \left[\sum_{v} h_v^{(K)}\ \Big\|\ \frac{1}{|V|}\sum_{v} h_v^{(K)}\right]$$

\item \textbf{Combined.}
    Concatenates NetLSD, WL and GIN descriptors ($3 \times 128 = 384$ dimensions) and reduces via PCA to the target dimension, by default 128.
    It aims to be most robust to individual embedder failures.
\item \textbf{CodeBERT (seq)}. Hugging Face downloaded Transformer sequence encoder from which the \texttt{[CLS]} token is used as an embedding vector. 
The model inputs is the CODE text collected from graph nodes with \texttt{diff\_weight} > 0.3.
The nodes are sorted by descending \texttt{diff\_weight} then line number, or BFS over \texttt{REACHING\_DEF} / \texttt{CFG} / \texttt{CDG} edges from high-importance seeds (flow-ordered variant), so CodeBERT's self-attention implicitly sees data-flow structure.
However, we prefer to use all the nodes for performance.
No graph structure features.

\item \textbf{CodeBERT (pattern)}. The CodeBERT embedding (768-d) is concatenated with a 34-dimension structural embedding generated by the \texttt{VulnPatternEmbedder}. The resulting 802-dimensional vector then passes through PCA to be reduced to a 128-dimensional vector. 
    The extracted structural features are organized into 5 groups and are computed from the CPG's edge connectivity:
    \begin{itemize}
        \item Vulnerability Flow Patterns (8 dimensions): detect common C/C++ vulnerability signatures using graph reachability.
    \end{itemize}

These detect common C/C++ vulnerability signatures using graph reachability, listed on \ref{tab:pattern_vuln_feature}.

The node classification is done via regex on \texttt{CODE} attributes of each node, for example:
\begin{itemize}
    \item \texttt{free\_nodes}: CALL nodes matching \texttt{(free | kfree | vfree | kvfree | delete | release)}
    \item \texttt{alloc\_nodes}: CALL nodes matching \texttt{(malloc | calloc | kmalloc | kzalloc | alloc | realloc | new)}
    \item \texttt{deref\_nodes}: IDENTIFIER nodes matching \texttt{\textbackslash*\textbackslash w|->} (pointer dereferences)
    \item \texttt{check\_nodes}: CONTROL\_STRUCTURE nodes matching \texttt{(if | assert | BUG\_ON | WARN\_ON | check)} or NULL checks
\end{itemize}
\item Edge Composition (8 dimensions): Counts the fraction of each edge type among edges incident to nodes. The edge types considered are the following: \texttt{AST}, \texttt{CFG}, \texttt{CDG}, \texttt{REACHING\_DEF}, \texttt{REF}, \texttt{ARGUMENT}, \texttt{RECEIVER}, \texttt{CALL}. By doing so, we can infer code sensitivity to a type of vulnerability, for example:  If there are many \texttt{REACHING\_DEF} edges, the vulnerability is data-flow sensitive; if many \texttt{CFG}, it's control-flow sensitive code.

\item Changed and Context Nodes Boundary (6 dimensions): The goal is to identify whether the change is at the source or the sink of the data/control flow. For each flow-type edge ( \texttt{CFG}, \texttt{CDG}, \texttt{REACHING\_DEF}), count edges crossing the boundary between changed and context nodes and then normalize it by the total number of boundary edges.

\section*{FAISS}

As an indexer, we used FAISS flat. It was built using batches of 32 graphs embeddings per index call. The index metric used is the cosine similarity. Because the vectors are L2-normalized, the cosine similarity boils down to the inner product. Give the L2-normalization formula:
$$\mathbf{x}_{\text{norm}} = \frac{\mathbf{x}}{\Vert{}\mathbf{x}\Vert{}_2} = \frac{\mathbf{x}}{\sqrt{\sum_{i=1}^{n} x_i^2}}$$
And the cosine similarity:
$$\text{Cosine Similarity} = \cos(\theta) = \frac{\mathbf{a} \cdot \mathbf{b}}{\Vert{}\mathbf{a}\Vert{} \Vert{}\mathbf{b}\Vert{}} = \frac{\sum_{i=1}^{n} a_i b_i}{\sqrt{\sum_{i=1}^{n} a_i^2} \sqrt{\sum_{i=1}^{n} b_i^2}}$$
 
Because by definition the $${\Vert{}\mathbf{x}\Vert{}_2}$$ = 1, the cosine formula becomes an inner product calculation:
$$\langle \mathbf{a}, \mathbf{b} \rangle = \mathbf{a} \cdot \mathbf{b} = \sum_{i=1}^{n} a_i b_i$$

The PCA-based embedders save the fitted PCA to reuse them on the inference time. Each vector indexes the following metadata: cve  identifier number, cwe identifier number, function name, project, variant, number of nodes nodes, plus any extra fields from \texttt{pair.meta}. 

\section*{Agent Architecture}

The agent receives the \texttt{retrieved context + vulnerable code} and is responsible for returning a *patch*.

Just like the retrieval, the generation code is built on top of abstractions that allow easier extention of different implementation for experimentation purposes.


We have three dataclasses trough which the flow passes:

\begin{itemize}
  \item PatchContext — the input packet: \texttt{example\_db} (the retrieved similar CVE's metadata), 
  \texttt{target\_db} (the CVE to fix), \texttt{target\_code} (vulnerable C source), 
  and optionally \texttt{graph\_context} $+$ \texttt{query\_pair} (CPG graphs for graph-aware variants).
  \item AgentResult — the output packet: `parsed` (the `PatchResult` with `cot` + \texttt{vuln\_patch}), `turns` (one `InvocationRecord` per LLM call), 
  \texttt{tool\_calls} (log of tool executions), \texttt{prompt\_fingerprint}, and token totals.
  \item Agent (Protocol) — anything with `.name` and `.run(ctx: PatchContext) -> AgentResult`. 
\end{itemize}

To allow the easy switch between different agents architecture, there is a \texttt{resgistry.py}
An architecture is identified by name and selectable via `--architecture` on the CLI or \texttt{config.yaml agents.architecture}:

The goal is to keep the architecture as simple as possible, so we are starting with a simple agent called \texttt{single\_turn} (located \text{single\_turn.py})
It consists of one LLM call, few-shot prompt and, a marker-parsed output.

\textbf{LLM-as-a-judge} evaluator inspired on ~\cite{google2026llmjudge}
Given the bug context (e.g., bug description), the patch in the unified diff     format [ 12 ], and the golden rubric as input, the LLM judge is instructed to output its validity assessment. The assessment consists of a “thought” section that captures its thinking steps, a binary label (“VALID” or “INVALID”), and a justification that captures its reasoning more concisely. We store the LLM judge’s output label and justification for further analyses, such as qualitatively understanding why certain patches are accepted or rejected


Hunk definition: A hunk is a block of consecutive edits applied to a specific region in the source code.  ~\cite{nashid2025characterizingmultihunkpatchesdivergence}
the change can be of two types:  deletion or addition

Hunk metrics calculation pipeline:
\noindent \textbf{Line Normalization:} \\
Normalize each line by collapsing whitespace and stripping:
\[
L = \{\text{norm}(l) : l \in \text{lines}, l \neq \emptyset\}
\]

\noindent \textbf{Change Extraction:}
\begin{align*}
\text{gold\_added} &= \text{ref\_lines} \setminus \text{base} \\
\text{gold\_removed} &= \text{base} \setminus \text{ref\_lines} \\
\text{gen\_added} &= \text{gen\_lines} \setminus \text{base} \\
\text{gen\_removed} &= \text{base} \setminus \text{gen\_lines} \\
\text{gold\_changed} &= \text{gold\_added} \cup \text{gold\_removed} \\
\text{gen\_changed} &= \text{gen\_added} \cup \text{gen\_removed}
\end{align*}

\noindent \textbf{Hunk F1 (line-level):}
\[
\text{hunk\_f1} = \frac{2 \cdot |\text{gen\_changed} \cap \text{gold\_changed}|}{|\text{gen\_changed}| + |\text{gold\_changed}|} \quad \text{(when both non-empty)}
\]

\noindent \textbf{Hunk Jaccard:}
\[
\text{hunk\_jaccard} = \frac{|\text{gen\_changed} \cap \text{gold\_changed}|}{|\text{gen\_changed} \cup \text{gold\_changed}|}
\]

\noindent \textbf{Hunk Token Jaccard:}
\[
\text{hunk\_token\_jaccard} = \frac{|\text{tokens}(\text{gen\_changed}) \cap \text{tokens}(\text{gold\_changed})|}{|\text{tokens}(\text{gen\_changed}) \cup \text{tokens}(\text{gold\_changed})|}
\]

\vspace{1em}
\noindent Plus separate F1 scores for \textbf{added} and \textbf{removed} lines using the same set-based formula.

\textbf{BERTScore} Measure Patch quality via embeddings

2 · P · R/P + R

Harmonic mean of contextualembedding-based precision and recall.

\textbf{Experiments Comparison between Methodologies}
Paired per-query deltas + a sign/Wilcoxon test — never compare aggregate means over different evaluated subsets (that was the original trap)
