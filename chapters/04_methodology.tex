\subsection*{Data Pipeline}

The process consists of, first, build the index, an offline process:

\begin{itemize}
  \item  loading a vulneral code snippet 
  \item build a CPG from the code
  \item embed the graph
  \item index the embeddings into a vector database, FAISS
\end{itemize}

then the online process consists of:
\begin{itemize}
  \item transform the code snippet input into an embedding
  \item query the vector database to find similar code, indicating they contain a similar vulnerability
  \item use the index data, especially the patched code to prompt an LLM to fix the vulnerability.
\end{itemize}

On development phase, it is also possible to evaluate retrieval and patch quality.

\subsection*{Graph Loading}
% content: NetworkX MultiDiGraph import, cleanups
This work utilizes Joern to generate the Code Property Graph (CPG) from a code snippet. 
For snippets that are not well-formed C/C++ programs, notably those from AutoPatch, the pipeline first wraps the code with the minimum necessary macros and type definitions (e.g. \ \verb|typedef unsigned int u32|, \verb|#define NULL ((void*)0)|) and writes a parseable source file.
The C/C++ code files are exported to a binary graph  with the Joern shell command \verb|joern-parse --language newc|, where \verb|newc| specifies the C++ specifities avoiding will-formed graphs.  
Then, the compiled graph is exported to GraphML format with the shell-command \verb|joern-export --repr cpg --format graphml|. 
Each export generates a directory tree where each subdirectory contains an \verb|export.xml| file with a subgraph of the the whole CPG. 
The nodes can have different labels (e.g.\ \verb|CALL|, \verb|IDENTIFIER|, \verb|CONTROL_STRUCTURE|), whereas the edges can belong to one of the following graph representation: 
Abstract Syntax Tree (AST), Control Flow Graph (CFG), Call Dependency Graph (CDG), and Program Dependency Graph (PDG). % TODO: define these graphs

The pipeline generates both \textit{vulnerable} and \textit{patched} code snippet graphs.  

\subsection*{Graph Loading}
The exported graph is imported into the pipeline using the NetworkX library as a \verb|MultiDiGraph|. %TODO: explain library 
All the export.xml discovered by recursively exploring the subdirectories. Once the graph they store is imported to the pipeline, it is merged by reading each file with \verb|nx.read_graph|and updating the combined graph iteratively. 
The NetworkX library considers each graph, node and edges as a dictionary and update the data structure by adding one graph set of nodes and edges at a time.
The Joern definition of the graph is, that is, the node and edge attributes, is conserved, therefore, the graph consistency depends on the Joern export. 
% The Joern-assigned node and edge attributes are preserved as-is;
% however, the multi-file export may contain edges referencing nodes
% outside the exported scope (e.g.\ language built-ins).
% The loader removes such attributeless stub nodes and their
% dangling edges to produce a self-contained graph.
Once the graph is loaded, the following cleanups are applied:
\begin{itemize}
  \item Nodes with the label \verb|COMMENT| or \verb|UNKNOWN| are removed
  \item Any remaining edges whose source or target were removed are pruned.
\end{itemize}

\subsection*{Graph Sampling}
Once the CPG is loaded, it contains the full code, including the boilerplate added in the pipelene.
Thefore it is necessary to isolate the subgraph related to the vulnerability from the irrelevant rest of the code. 
For that, a subsample is calculated from the difference between the vulnerable graph and the patched graph, the so called $G_{\mathrm{vuln}}$. 
By doing so we expect to be able to generalize the search for the vulnerability removing the specificities of a given system that are inprint in the graph.

\paragraph{Bounded slicing}
To include context that may be relevant, a bounded search is performed with the goal of include any relevant settings in which the vulnerability occurs.
The slice is a configurable neighbourhood expansion ($n \in \{0,1,2,3\}$ hops). $n=0$ is the original sampled graph, that is, only directly changed nodes.
    
\paragraph{Semantic difference}
Before perform the sampling, each node needs to be deterministically identifiable to avoid different results depending on runs or randomness resulting from non-deterministic ID assigned by Joern across runs.
The nodes in the sample are further enriched with semantic labels resulting of the two graphs comparison.
Each node of the sample is labeled as either:
\begin{itemize}
  \item Removed node: every node present in $G_\mathrm{orig}$ but absent in the $G_\mathrm{patch}$.
  \item Fix-adjacent node: every node present in $G_\mathrm{orig}$ that is a removed node neighbor.
  \item Edge-changed node: every node attached to an edge which any of the nodes changed between the two graphs. 
\end{itemize}

Besides the labelling, the $G_\mathrm{vuln}$ nodes also received weights. 
\begin{center}
\begin{tabular}{lc}
  \textbf{Label} & \textbf{Weight} \\
  \hline
  \texttt{removed}       & 1.0 \\
  \texttt{fix\_adjacent} & 0.8 \\
  \texttt{edge\_changed} & 0.6 \\
  \texttt{context}       & 0.2 \\
\end{tabular}
\end{center}

These weights are directly proportional to the relation of the node to the vulnerability and will be integrated to the embedders for further prunning.

\subsection*{Embedders}
% content ONLY: your config choices --
% - 128-dim, L2-normalized, configurable PCA (shared preamble)
% - "Combined" embedder: concatenation (384d) + PCA reduction, robustness rationale
% - CodeBERT (seq) variant: your pipeline diagram/config

For reference, we started with deterministic embedders that work either with heuristics or with well-defined mathematical formulations.
All embedders are \textbf{unsupervised}, that is, no labelled training data required.
By default their output is L2-normalised vectors with a default dimension of 128, but configurable.
Besides that, the embedding may have a PCA.

\begin{itemize}

  \item \textbf{NetLSD} (\textit{Network Laplacian Spectral Descriptor}) ~\cite{netlsd}.
  Computes the heat trace of the normalised graph Laplacian across a timescale that aims to get graph expressive representations similar to random walk models.
  It is node permutation-invariant and captures global spectral structure, adapting to scale encoding both local and global features, that is, it is scale-adaptable. 
  It is also capable of comparing different size graphs. It supports weighted graphs. 
  It was created to be an alternative to the NP-approach graph edit distance, being then efficiently computable, so the comparison calculation happens in a constant time. 

  \item \textbf{WL} (\textit{Weisfeiler-Lehman Kernel}).
    Iterative colour refinement over node types followed by weighted sum pooling and a linear projection. 
    In this work, it was implemented in PyTorch Geometric with no external dependency. 
    % \texttt{diff\_weight} biases pooling toward high-signal nodes.
    WL test iteratively : 
    (1) aggregates the labels of nodes and their neighborhoods, 
    and (2) hashes theaggregated labels into unique new labels

  \item \textbf{GIN} (\textit{Graph Isomorphism Network}) ~\cite{xu2019gin}
   Message-passing neural Network that is as powerful as the Weisfeiler-Lehman graph isomorphism test, which evaluates whether two graphs are topologically identical.
    A Graph Neural Network that represents each node by recursively aggregating the neighboring represention. 
    The node representation is updated at each layer k, by aggregating the representations of its neighbors via a sum aggregator, followed by an MLP:
    $$h_v^{(k)} = \text{MLP}^{(k)}\!\left((1+\epsilon)\cdot h_v^{(k-1)} + \sum_{u \in \mathcal{N}(v)} h_u^{(k-1)}\right)$$

  Where $\epsilon$ is either a learnable paramet or a fixed scalar (TODO: check what is the case here).
  $h_v^{(0)}$ is initialized from the node features. (TODO: explain network initialization).
  The number of layers is equivalent to the number of neighbor hops that will be encoded by each node.
  This choice is a trade-off of the amount of local structural pattern against the global one.  
  Therefore it learns to embed the subtree in a low dimensional space, not only discriminating different structures but also mapping similar embeddings for similar structures and capturing dependencies between graph structures.
  Graph-level embeddings are obtained via dual pooling concatenating sum pooling and mean pooling outputs. 
  The sum pooling preserves structural size information, while mean pooling makes the normalized representations normalized.
  $$\mathbf{h}_G = \left[\sum_{v} h_v^{(K)}\ \Big\|\ \frac{1}{|V|}\sum_{v} h_v^{(K)}\right]$$

\subsection*{Agent Architecture}
the agent may never call the $submit\_patch$, what might result in a parser error in the evaluator, since there is not patch snippet to be evaluated.

The pipeline was implemented in layers that are cleanly separated.
In a larger scale, we can split the pipeline in retrieval and generation, where the retrieval happens independently and before the agent ever runs.
The agent's receives the \texttt{retrieved context + vulnerable code} and is responsible to return a *patch*.

Just like the retrieval, the generation code is built on top of abstractions that allow easier extention of different implementation for experimentation purposes.


We have three dataclasses trough which the flow passes:

\begin{itemize}
  \item PatchContext — the input packet: \texttt{example\_db} (the retrieved similar CVE's metadata), 
  \texttt{target\_db} (the CVE to fix), \texttt{target\_code} (vulnerable C source), 
  and optionally \texttt{graph\_context} $+$ \texttt{query\_pair} (CPG graphs for graph-aware variants).
  \item AgentResult — the output packet: `parsed` (the `PatchResult` with `cot` + \texttt{vuln\_patch}), `turns` (one `InvocationRecord` per LLM call), 
  \texttt{tool\_calls} (log of tool executions), \texttt{prompt\_fingerprint}, and token totals.
  \item Agent (Protocol) — anything with `.name` and `.run(ctx: PatchContext) -> AgentResult`. 
\end{itemize}

To allow the easy switch between different agents architecture, there is a \texttt{resgistry.py}
An architecture is identified by name and selectable via `--architecture` on the CLI or \texttt{config.yaml agents.architecture}:

The goal is to keep the architecture as simple as possible, so we are starting with a simple agent called \texttt{single\_turn} (located \text{single\_turn.py})
It consists of one LLM call, few-shot prompt and, a marker-parsed output.

\paragraph{Structure-aware tooling.}

ReAct~\cite{react2023google} loop where the LLM reasons and calls tools iteratively until it reaches a submition point and it calls \texttt{submit\_patch}.
It may also happen that the agent hits the maximum number of iterations, which is set to 6.

\centering
\begin{tabularx}{\textwidth}{l X}
  \toprule
  \textbf{Tool} & \textbf{Functionality} \\
  \midrule
  \texttt{get\_vulnerability\_context} & Returns CVE description, CWE category, and typical fix patterns from the static knowledge base (\texttt{cwe\_descriptions.py}). It covers CWE-20/190/362/400/416/476/787 \\
  \addlinespace
  \texttt{analyze\_example\_fix} & Calculate the difference between \texttt{example\_db.original\_code} and \texttt{example\_db.vuln\_patch} and returns a structured unified diff (truncated to a token budget). Also return a record of the fixes (\texttt{fix\_list}) \\
  \addlinespace

\end{tabularx}

\paragraph{Backend abstraction.}
The pipeline has a LLM Transport (\texttt{src\/agents\/backends.py}) abstraction that is defined by a protocol (\texttt{CompletionBackend}) that allows different LLM completion.
With this we can run part of the pipeline without rerun the whole pipeline. 
Also, it allows record and mocked responses so we can experiment only part of the pipeline without incurring high costs
The \texttt{complete()} signature was extended with \texttt{tools=} and \texttt{tool\_choice=} kwargs, so the same backend handles both architectures. 
Four implementations:

\begin{table}[ht]
 \caption[Types of API call Table]{An example for a simple table.}\label{tab:sample}

\centering
\begin{tabularx}{\textwidth}{l X}
  \toprule
  \textbf{Backend} & \textbf{Function} \\
  \midrule
  \texttt{LiveBackend} & Azure/litellm call (lazy import) \\
  \addlinespace
  \texttt{MockBackend} & Deterministic output for unit tests \\
  \addlinespace
  \texttt{RecordBackend} & Wraps Live, records to JSONL cassette \\
  \addlinespace
  \texttt{ReplayBackend} & Reads from cassette, zero network  \\
\end{tabularx} 
\end{table}

To swap between backends, it is only necessary to call \texttt{use\_backend()} context manager, no other call change is needed.
