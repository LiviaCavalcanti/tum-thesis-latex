\chapter{Methodology}\label{chapter:methodology}

One of the goals of this work is to use historical knowledge from previous fixes to generate fixes for new, structurally similar vulnerable code.

\section{Architecture}
% content: KB + agentic framework description
This project presents a structure-aware retrieval system that identifies the type of vulnerability in a code snippet and suggests a patch grounded in similar previously seen fixes. 
These previously fixed code snippets are used to build a knowledge base (KB) indexed with embeddings built from the code. This knowledge base is combined with an agentic generation layer that, given the context retrieved, prompts an LLM to produce a candidate patch.

\section{Data Pipeline}

Following the architecture definition, the data pipeline was implemented in separate layers: Retrieval and Generation.
Besides that, the system can be split into offline retrieval-index construction of the KB, and an online stage in which retrieval occurs independently, before the patch generation.

\paragraph{Offline index construction.} Building the index process consists of:

\begin{itemize}
  \item loading a vulnerable code snippet; 
  \item building a CPG from the code;
  \item embedding the graph;
  \item indexing the resulting embeddings into a vector database (FAISS).
\end{itemize}

\paragraph{Online Query and generation.} At inference time, the pipeline runs the following steps:
\begin{itemize}
  \item transforms the input (query) code snippet into an embedding;
  \item queries the vector database to retrieve the closest historical example, indicating they contain a similar underlying vulnerability;
  \item prompts an LLM to generate a fix for the query vulnerability, combining (a) the retrieved example's own metadata, notably the retrieved patched code, CWE, CVE identifier, root cause, and variable/function mappings, with (b) the query's own CWE (plus, where the query is drawn from the curated AutoPatch subset, its own root cause and variable/function mappings), as described in the Architecture section above.
\end{itemize}

In the development phase, retrieval and patch can be assessed on a held-out test set using the automated evaluation script described in ~\ref{section:evaluation}.

\section{Graph Representation}\label{sec:graph-representation}

\subsection{Graph Generation}\label{sec:graph-generation}

This work uses Joern to generate the Code Property Graph (CPG) from a code snippet. 
For snippets that are not well-formed C/C++ programs, notably those from AutoPatch, the pipeline first wraps the code with the minimum necessary macros and type definitions (e.g. \ \verb|typedef unsigned int u32|, \verb|#define NULL ((void*)0)|) and writes a parseable source file.

The resulting C/C++ file is compiled into a binary graph representation with the Joern shell command \verb|joern-parse --language newc|, where \verb|newc| is used to handle C\/C++ language constructs and to avoid malformed graphs.  
Then, the compiled graph is exported to GraphML format with the shell command \texttt{joern-export --repr cpg --format graphml}. 
Each export generates a directory tree where each subdirectory contains an \verb|export.xml| file with a subgraph of the full CPG.

The nodes can have different labels (e.g.\ \verb|CALL|, \verb|IDENTIFIER|, \verb|CONTROL_STRUCTURE|), while the edges can belong to one of the following graph representations layered over the same node set: 
Abstract Syntax Tree (AST), Control Flow Graph (CFG), Control Dependence Graph (CDG), and Program Dependency Graph (PDG).
\begin{itemize}
    \item AST: syntactic parse structure of the source code.
    \item CFG: possible execution paths through the code (branches, loops).
    \item CDG: control-dependency relationships between statements (which conditionals govern which statements' execution).
    \item PDG: data- and control-dependency edges combined, capturing both what controls a statement's execution and what data it depends on.
\end{itemize}

The pipeline generates graphs for both the \textit{vulnerable} and the \textit{patched} version of each code snippet.  


\subsection{Graph Loading}
The exported graph is imported into the pipeline using the NetworkX library as a \verb|MultiDiGraph|, a directed graph representation that allows multiple parallel edges between the same pair of nodes, which allows the representation of multiple code graph structure since (e.g.\ both an AST and a CFG edge).

All  \verb|export.xml| files are discovered by recursively exploring the export's subdirectories. Each file is read individually with \verb|nx.read_graphml| and merged into a single combined graph iteratively. 
The NetworkX library represents each graph, node, and edge as dictionaries. Therefore, each merge updates the dictionaries with the loaded graph's entries.

 
% The Joern-assigned node and edge attributes are preserved as-is;
% however, the multi-file export may contain edges referencing nodes
% outside the exported scope (e.g.\ language built-ins).
% The loader removes such attributeless stub nodes and their
% dangling edges to produce a self-contained graph.
Once the graph is loaded, the following cleanups are applied:
\begin{itemize}
  \item nodes labeled with \verb|COMMENT| or \verb|UNKNOWN| are removed;
  \item any remaining edges whose source or target in previous step are removed are pruned.
\end{itemize}

\section{Embedders}

Two embedding families were evaluated: deterministic embedders, built on heuristics or well-defined mathematical formulations, and semantic embedders, built on pretrained language model of code.
All embedders are \textbf{unsupervised}, that is, no labeled training data required.
By default, each embedder output is an L2-normalized vector with a dimension of 128.
This vector is then passed through the PCA reduction step.

\begin{itemize}

  \item \textbf{NetLSD} (\textit{Network Laplacian Spectral Descriptor}) ~\cite{netlsd}, introduced in Chapter~\ref{chapter:literature-review}.
  The heat trace signature is evaluated at 128 log-spaced timescales $t \in [10^{-2}, 10^{2}]$ (\texttt{numpy.logspace(-2, 2, 128)}), yielding one scalar per timescale as the descriptor dimension. Before computing the trace, isolated nodes are removed from the undirected projection of the CPG, since they inflate the zero eigenvalue and collapse the descriptor; graphs with fewer than 3 remaining nodes are embedded as the zero vector.

  \item \textbf{WL} (\textit{Weisfeiler-Lehman Kernel}), following the $1$-WL color-refinement process described in Chapter~\ref{chapter:literature-review}.
    Implemented via iterative color refinement over node types, followed by weighted sum pooling (\texttt{global\_add\_pool}) and a linear projection. 
    In this work, it was implemented in PyTorch Geometric with no external dependency. 
    % \texttt{diff\_weight} biases pooling toward high-signal nodes.
    As input, it receives  11-class one-hot over CPG node types (METHOD, CALL, IDENTIFIER, etc.) which can be, optionally, enriched with one-hot encoding 5-dimension diff-label and a 1-dimension \texttt{diff\_weight} scalar, resulting in 17 dims per node. The pipeline uses it untrained with the random weights fixed at seed 42.
  Concretely, the implementation stacks 4 \texttt{WLConv} refinement layers (PyTorch Geometric); each layer's resulting colour is hashed modulo an 8192-entry embedding table (\texttt{hidden\_dim}=64) to keep the representation bounded. The 4 per-iteration sum-pooled vectors ($4 \times 64 = 256$d) are concatenated and passed through a single \texttt{Linear(256, 128)} projection layer. All weights (embedding table and projection) are randomly initialized with \texttt{torch.manual\_seed(42)} and never trained.

  \item \textbf{GIN} (\textit{Graph Isomorphism Network}) ~\cite{xu2019gin}, introduced in Chapter~\ref{chapter:literature-review}.
    The node representation is updated at each layer \texttt{k} by aggregating the representations of its neighbors via a sum aggregator, followed by an MLP:
    $$h_v^{(k)} = \text{MLP}^{(k)}\!\left((1+\epsilon)\cdot h_v^{(k-1)} + \sum_{u \in \mathcal{N}(v)} h_u^{(k-1)}\right)$$

  Where $\epsilon$ is a fixed scalar ($\epsilon = 0$, \texttt{train\_eps=False}) rather than a learned parameter, consistent with the embedder being used untrained.
  $h_v^{(0)}$ is initialized  from the node features, i.e.\ the 11-dimensional one-hot CPG node-type encoding described above.
  Concretely, the network stacks $K=3$ \texttt{GINConv} layers, each with a hidden dimension of 128 and followed by a \texttt{BatchNorm1d} and ReLU. All weights (input projection, MLPs, readout) are randomly initialized once with \texttt{torch.manual\_seed(42)}, frozen (\texttt{requires\_grad=False}), and reused as a fixed feature extractor across all graphs, consistent with the untrained-GIN literature that shows random GIN weights already produce structurally discriminative embeddings.
  Graph-level embeddings are obtained via dual pooling, concatenating sum pooling and mean pooling outputs. 
  The sum pooling preserves structural size information, while mean pooling makes the normalized representations.
  $$\mathbf{h}_G = \left[\sum_{v} h_v^{(K)}\ \Big\|\ \frac{1}{|V|}\sum_{v} h_v^{(K)}\right]$$

\item \textbf{Combined.}
    Concatenates NetLSD, WL and GIN descriptors ($3 \times 128 = 384$ dimensions) and reduces via PCA (\texttt{sklearn.decomposition.PCA}, \texttt{random\_state=42}) to the target dimension, by default 128. The PCA is fit once on the first batch of graphs seen (\texttt{embed\_many()}/\texttt{fit()}) and its parameters are cached and reused at inference time.
    It aims to be most robust to individual embedder failures.
\item \textbf{CodeBERT (seq)}. Uses the local \texttt{microsoft/codebert-base} checkpoint cached at \texttt{models/codebert-base/} (loaded with \texttt{AutoModel.from\_pretrained(..., local\_files\_only=True)}), from which the \texttt{[CLS]} token of the last hidden state is used as the 768-d embedding vector. No graph-structural features are used; this variant is the semantic-only ablation control.

\paragraph{Node selection and ordering (as run).} The model input is built by \texttt{collect\_changed\_code()}: nodes with \texttt{diff\_weight > 0.3} are kept and sorted by (descending \texttt{diff\_weight}, ascending \texttt{LINE\_NUMBER}); their \texttt{CODE} strings are concatenated in that order up to a \textbf{400-whitespace-token} budget (truncating the last node's text if it would exceed the budget). \emph{Fallback only:} if no node exceeds the 0.3 threshold, every code-bearing node is used instead, ordered by line number alone. All experiments reported here use this line/diff-weight ordering; the BFS flow-ordered variant that traverses \texttt{REACHING\_DEF}/\texttt{CFG}/\texttt{CDG} edges from high-\texttt{diff\_weight} seeds (\texttt{collect\_flow\_ordered\_code()}, exposed as \texttt{codebert\_flow}) was implemented but not part of \texttt{embeddings.active} in \texttt{config.yaml} and is not used for the reported results.

\paragraph{Tokenization.} The concatenated string is then passed to the CodeBERT tokenizer with \texttt{truncation=True, max\_length=512} (subword tokens, batched with padding). The 400-word pre-truncation and the 512-subword tokenizer truncation are two independent, stacked limits — the former bounds how much raw code is concatenated per node, the latter bounds the final subword sequence fed to the transformer.

\paragraph{Duplicated tokens.} Because Joern assigns a \texttt{CODE} span to every AST node (statements, sub-expressions, identifiers, literals), concatenating over all qualifying nodes reproduces overlapping text: e.g.\ a \texttt{CALL} node's full expression text and its child \texttt{IDENTIFIER}/\texttt{LITERAL} nodes' sub-spans are \emph{both} concatenated, so tokens are duplicated across nesting levels in the flattened sequence. No de-duplication is applied.

When a projection to 128d is requested, the 768-d CLS vectors are reduced with a PCA (\texttt{sklearn.decomposition.PCA}, \texttt{random\_state=42}) fit once on the index corpus (\texttt{embed\_many()}/\texttt{fit()}) and reused at query time.

\item \textbf{CodeBERT (pattern)}. The CodeBERT embedding (768-d) is concatenated with a 34-dimension structural embedding generated by the \texttt{VulnPatternEmbedder}. Its 768-d CodeBERT component reuses the same checkpoint, node selection/ordering, tokenization, and query-time diff-weight assumptions of CodeBERT (seq) described above (\texttt{collect\_changed\_code()}, \texttt{max\_length=512}). The resulting 802-dimensional vector then passes through PCA (\texttt{sklearn.decomposition.PCA}, \texttt{random\_state=42}, fit once on the index corpus) to be reduced to a 128-dimensional vector. 
    The extracted structural features are organized into 5 groups and are computed from the CPG's edge connectivity:
    \begin{itemize}
        \item Vulnerability Flow Patterns (8 dimensions): detect common C/C++ vulnerability signatures using graph reachability.
    \end{itemize}

The node classification is done via regex on \texttt{CODE} attributes of each node, for example:
\begin{itemize}
    \item \texttt{free\_nodes}: CALL nodes matching \texttt{(free | kfree | vfree | kvfree | delete | release)}
    \item \texttt{alloc\_nodes}: CALL nodes matching \texttt{(malloc | calloc | kmalloc | kzalloc | alloc | realloc | new)}
    \item \texttt{deref\_nodes}: IDENTIFIER nodes matching \texttt{\textbackslash*\textbackslash w|->} (pointer dereferences)
    \item \texttt{check\_nodes}: CONTROL\_STRUCTURE nodes matching \texttt{(if | assert | BUG\_ON | WARN\_ON | check)} or NULL checks
\end{itemize}
\item Edge Composition (8 dimensions): Counts the fraction of each edge type among edges incident to nodes. The edge types considered are the following: \texttt{AST}, \texttt{CFG}, \texttt{CDG}, \texttt{REACHING\_DEF}, \texttt{REF}, \texttt{ARGUMENT}, \texttt{RECEIVER}, \texttt{CALL}. By doing so, we can infer code sensitivity to a type of vulnerability, for example:  If there are many \texttt{REACHING\_DEF} edges, the vulnerability is data-flow sensitive; if many \texttt{CFG}, it's control-flow sensitive code.

% ```
% edge_fracs[i] = count(edge_type[i] touching changed nodes) / total_edges_touching_changed
% ```

\item Changed and Context Nodes Boundary (6 dimensions): The goal is to identify whether the change is at the source or the sink of the data/control flow. For each flow-type edge ( \texttt{CFG}, \texttt{CDG}, \texttt{REACHING\_DEF}), count edges crossing the boundary between changed and context nodes and then normalize it by the total number of boundary edges.

% ```
% CFG[0] = count(changed → context via CFG)
% CFG[1] = count(context → changed via CFG)
% CDG[2..3], REACHING_DEF[4..5] — same pattern
% ```

\item Topology Stats (6 dimensions): embeds the characteristics of the graph, for example, edge density, number of connected components, mean degree, max degree, and internal and crossing.

\item Node Role Distribution (6 dimensions): counts the types of nodes (\texttt{CALL}, \texttt{OTHER}, \texttt{IDENTIFIER}, \texttt{CONTROL\_STRUCTURE}, \texttt{LITERAL}, \texttt{BLOCK})
\end{itemize}

\section{Retrieval Index}

As an indexer, we used FAISS flat. It was built using batches of 32 graphs embeddings per index call. The index metric used is the cosine similarity. Because the vectors are L2-normalized, the cosine similarity boils down to the inner product. 
The L2-normalization formula:
$$\mathbf{x}_{\text{norm}} = \frac{\mathbf{x}}{\Vert{}\mathbf{x}\Vert{}_2} = \frac{\mathbf{x}}{\sqrt{\sum_{i=1}^{n} x_i^2}}$$
And the cosine similarity:
$$\text{Cosine Similarity} = \cos(\theta) = \frac{\mathbf{a} \cdot \mathbf{b}}{\Vert{}\mathbf{a}\Vert{} \Vert{}\mathbf{b}\Vert{}} = \frac{\sum_{i=1}^{n} a_i b_i}{\sqrt{\sum_{i=1}^{n} a_i^2} \sqrt{\sum_{i=1}^{n} b_i^2}}$$
 
Because by definition the $${\Vert{}\mathbf{x}\Vert{}_2}$$ = 1, the cosine formula becomes an inner product calculation:
$$\langle \mathbf{a}, \mathbf{b} \rangle = \mathbf{a} \cdot \mathbf{b} = \sum_{i=1}^{n} a_i b_i$$

The PCA-based embedders save the fitted PCA to reuse it on inference time. Each vector indexes the following metadata: CVE identifier number, CWE identifier number, function name, project, variant, number of nodes, plus any extra fields from \texttt{pair.meta}. 

The index is stored as a binary, and the metadata as a JSON file. Each position in the vector index corresponds to an entry in the metadata. At retrieval time, both are loaded, allowing semantic-metadata mapping for operations enrichment.

\section{Agent Architecture}\label{section:agent-architecture}

The agent receives the retrieved context, if applicable, and the vulnerable code, and is responsible for returning a candidate patch.

Just as with retrieval, the generation code is built on top of abstractions that allow easy extension with different implementations for experimentation.


Three data classes carry the flow through the pipeline and standardize the information handling:

\begin{itemize}
  \item \textbf{PatchContext}: wraps what is required to generate a patch and, therefore, will be used as the input for the agent. It includes the retrieved example's own metadata (CWE, CVE identifier, root cause, variable/function mappings, and patched code), the vulnerable C source to patch, the target's CWE (and, when available from the curated AutoPatch subset, the target's own root cause and variable/function mappings, as introduced in the Architecture section), and, for graph-aware variants, the CPG graph context.
  \item \textbf{AgentResult}: wraps the output data consisting of Chain of Thought and the vulnerable code, the patched code, each of the LLM call turns ( \texttt{InvocationRecord} format), log of tool call executions along with prompt fingerprints, and the total number of tokens.
\item \textbf{Agent}: base class that works as a Protocol containing the agent name and a run method implementation that receives a \texttt{PatchContext} as input and generates a \texttt{AgentResult} object. With that, it is possible to easily integrate different agent approaches by following the pipeline's interface while maintaining the observability necessary for performance evaluation.  
\end{itemize}

To allow easy switching between different agent architectures, implementations are registered in \texttt{resgistry.py} and selected either by name \texttt{--architecture} on the CLI or \texttt{agents.architecture} in \texttt{config.yaml}:

The work developed two agent implementations \texttt{Single Turn}, a minimal one-shot baseline, and a \texttt{Tool Calling} agent, which uses ReAct loops with access to coding tools.

\subsection{Single-turn LLM}

The baseline prompt uses the Autopatch paper's approach as reference, and is powered by an LLM(GPT-4o, temperature=0.2). 
The AutoPatch approach separates the example from the system instructions, allowing the LLM to clearly distinguish between what the task is, the example, and the target input. To do so, the approach uses a few-shot prompt and builds 4 messages assembled from template files declared in \texttt{registry.yaml}, a record of historically available prompt templates. 

The first prompt is a system message that establishes the persona and task of the agent. It contains the CWE of the retrieved example, the CVE identifier of the retrieved example, and symbolic, variable-agnostic fix steps extracted from the example stored in JSON (present in the AutoPatch dataset).
The system prompt instructs step-by-step reasoning ending with a structured output. 

After that, the user messages are passed to the model using their own templates. The first user message (user\_example.txt) contains the retrieved example as the few-shot demonstration.
This includes concrete variable name substitutions, concrete function name substitutions, root cause description of the example CVE, and vulnerable C source of the example.

Another prompt template, called \texttt{Assistant message}, provides a pre-filled model answer for the example with the expected reasoning style. 
It includes  chain-of-thought reasoning for the example fix and gold patched code as template fields.
The assistant template also includes directive for the expected reasoning format: \texttt{"in the following format, including the leading and trailing ``` ... [CoT START] ... [Patched Code START] ... [Patched Code END]"}. By using separate templates, the formatting structure is preserved and clearly distinguished throughout the conversation.

The second user message contains the actual code to be patched. 
It has the same structure as the first user message, but with the fields: target code, target root cause, target vulnerability-related variable mapping, target vulnerability-related function mapping, and target supplementary code. As established in the Architecture section, only the target's CWE (used to build the system prompt) is assumed known for every query; the target root cause and variable/function mapping fields are populated only when the query is drawn from the curated AutoPatch subset, which carries these per-CVE annotations, and default to \texttt{"Unknown"} for CVEfixes-sourced queries.

The use of multiple messages also allows generalization of the naming convention in the target code. The example's variable/function mappings, in both system prompt and first user message, teach the model how to adapt from abstract fix patterns (from the example) to concrete variable names in the target code.


The system also includes a second version that adds an explicit verification step to promote reasoning and error fixing.
In this version, the system prompt also contains an explicit sub-step: \texttt{"Confirm your plan addresses the Root Cause and covers all instances of the bug pattern in the function."} The assistant message prompt inserts an explicit verification sub-step between CoT and patch generation: \texttt{"Step 2. Verify the plan. a) Root cause addressed? b) API compliance? c) Resource ownership?"}

\subsection{Agent with Structure-Aware Tooling}

This agent follows the ReAct loop~\cite{yao2023react} introduced in Chapter~\ref{chapter:literature-review}, in which the LLM reasons and calls tools iteratively until it reaches a submission point and calls \texttt{submit\_patch}, or until it hits the maximum number of iterations, set to 6.

The agent calls follow the OpenAI function-calling format. 
At each iteration, the agent calls \texttt{backend.complete(model, messages, tools=full\_tools, tool\_choice="auto")} passing the five tool schemas. 
The response is then dispatched based on the \texttt{finish\_reason}.
If the LLM's response includes \texttt{tool\_calls}, the respective tool call will be executed and appended to the conversation as \texttt{assistant} and \texttt{tool} messages.

The loop terminates when one of the four reasons is met: 
\begin{enumerate}
    \item the agent calls \texttt{submit\_patch}, exiting the loop with the resconstructed patch;
    \item the agent returns \texttt{finish\_reason=\"stop\"} and no tool calls are made, triggering a fallback code extraction.
    \item \texttt{finish\_reason=\"length\"} on the final iteration, the LLM response extrapolates the token limit, and a recovery prompt instructs the model to respond in a shorter fashion. If any iterations remain, the loop continues;
    \item unexpected \texttt{finish\_reason}, ending with failure.
\end{enumerate}

\paragraph{Patch representation and materialization.} The patch output follows a SEARCH\&REPLACE block format. 
Each \texttt{submit\_patch} output contains one or more blocks in the following format:

\begin{verbatim}
<<<<<<< SEARCH
[exact verbatim lines from target_code]
=======
[replacement lines]
>>>>>>> REPLACE
\end{verbatim}

This format has a couple of advantages. First, compared to returning the full code, which in many cases can be lengthy, it avoids truncation errors, any "generation errors" that change non-vulnerable code, and, ultimately, unnecessary output token costs. Second, compared to standard unified diff, it is required to add to the header the exact lines of change, which can lead to frequent hallucinations and makes it more difficult to reconstruct original code files if only a snippet was passed.  

The SEARCH\&REPLACE pairs are extracted via regular expression and applied to the target code in sequence using string matching.
If any SEARCH block does not match the input code verbatim, the submission is rejected with error feedback sent to the model as the tool result. 
This allows iterative refinement.
As the next step, the model re-enters the loop to correct the SEARCH block, by using the \ref{lst:patch-instructions} prompt and resubmit it.
If the match succeeds, the reconstructed patched file is returned as result and the loop ends.

\subsection{Retrieval Metrics}
\textbf{CWE hit@1} measures whether the top-1 retrieved example shares the same CWE category as the queried vulnerability.

\textbf{CVE hit@1} is a stricter version of the CWE hit@1. It measures whether the top-1 retrieved example corresponds to the same underlying CVE (or CVE-fix pair) as the query, rather than merely the same vulnerability class.
It is implemented as an exact CVE identifier match rather than fix-commit lineage, so every entry filed under the same CVE (e.g.\ multiple affected functions from the same fix) counts as a hit.

\textbf{Confidence Score} is the similarity score assigned by the retriever to its top-1 match, used to measure the ranking signal quality. It can also be used as a threshold to reject low-confidence retrievals rather than return wrong CVEs examples.

\textbf{MAP} (\textit{Mean Average Precision}) measures ranking quality rather than a single top-1 hit, and remains computable even when only one result is retrieved per query. For a single query, Average Precision at rank $k$ is:
\[
\text{AP@}k = \frac{1}{n_\text{rel}} \sum_{i=1}^{k} P(i) \cdot \text{rel}(i)
\]
where $\text{rel}(i) \in \{0, 1\}$ marks whether the result at rank $i$ shares the query's CVE, $P(i)$ is the precision (fraction of relevant results) within the top-$i$ results, and $n_\text{rel}$ is the number of relevant results retrieved (used as the denominator instead of the theoretical total so that AP@$k=1$ whenever every retrieved relevant result is ranked first).
MAP is then the mean of AP@$k$ over a group of queries; grouping by CVE (rather than averaging over the whole query set) yields the per-CVE MAP scores reported in the \texttt{cve\_map\_by\_cve} plots in Chapter~\ref{chapter:results}, which surface which individual vulnerabilities are reliably retrieved versus consistently missed.

\paragraph{Embedding-space sanity check.} Before running retrieval, the \textbf{Effective dimensionality} of an embedder's output space is inspected as a diagnostic: the participation ratio of the eigenvalues of the embedding covariance matrix,
\[
\text{PR} = \frac{\left(\sum_i \lambda_i\right)^2}{\sum_i \lambda_i^2},
\]
where $\text{PR}=1$ indicates a collapsed space (all variance along one direction) and $\text{PR}=d$ indicates that all $d$ nominal dimensions are used uniformly \cite{ansuini2019intrinsic}. This is used to catch degenerate embedders (e.g.\ a PCA fit on too few or too homogeneous graphs) before they are passed to retrieval, rather than as a metric with results reported in this work; per-embedder effective-dimensionality values are left as a diagnostic to report alongside future retrieval runs.

\subsection{Patching Metrics}

\textbf{LLM-as-a-judge.} following the evaluator design of ~\cite{google2026llmjudge}.
The evaluator receives the bug context (e.g., bug description) and the candidate patch. The LLM judge is instructed to output its validity assessment, which consists of a “thought” section capturing its thinking steps, a binary label (“VALID” or “INVALID”), and a concise justification. 
Both label and justification are stored for further analyses, such as finding patterns of why certain patches are accepted or rejected, related to code language or structure.


\textbf{Hunk-level metrics}: A hunk is a block of consecutive edits applied to a specific region in the source code\cite{nashid2025characterizingmultihunkpatchesdivergence}. 
Each change can be either and a deletion or an addition.

Hunk metrics calculation pipeline:
\noindent \textbf{Line Normalization:} \\
Normalize each line by collapsing whitespace and stripping:
\[
L = \{\text{norm}(l) : l \in \text{lines}, l \neq \emptyset\}
\]

\noindent \textbf{Change Extraction:}
\begin{align*}
\text{gold\_added} &= \text{ref\_lines} \setminus \text{base} \\
\text{gold\_removed} &= \text{base} \setminus \text{ref\_lines} \\
\text{gen\_added} &= \text{gen\_lines} \setminus \text{base} \\
\text{gen\_removed} &= \text{base} \setminus \text{gen\_lines} \\
\text{gold\_changed} &= \text{gold\_added} \cup \text{gold\_removed} \\
\text{gen\_changed} &= \text{gen\_added} \cup \text{gen\_removed}
\end{align*}

\noindent \textbf{Hunk F1 (line-level):}
\[
\text{hunk\_f1} = \frac{2 \cdot |\text{gen\_changed} \cap \text{gold\_changed}|}{|\text{gen\_changed}| + |\text{gold\_changed}|} \quad \text{(when both non-empty)}
\]

\noindent \textbf{Hunk Jaccard:}
\[
\text{hunk\_jaccard} = \frac{|\text{gen\_changed} \cap \text{gold\_changed}|}{|\text{gen\_changed} \cup \text{gold\_changed}|}
\]

\noindent \textbf{Hunk Token Jaccard:}
\[
\text{hunk\_token\_jaccard} = \frac{|\text{tokens}(\text{gen\_changed}) \cap \text{tokens}(\text{gold\_changed})|}{|\text{tokens}(\text{gen\_changed}) \cup \text{tokens}(\text{gold\_changed})|}
\]

\vspace{1em}
\noindent Plus separate F1 scores for \textbf{added} and \textbf{removed} lines using the same set-based formula.

\textbf{BERTScore} Measure Patch quality via embeddings, complementing the overlap lines evaluation. It consists of the F1-score metric, considering the contextual embedding precision and recall. 

\[
\text{BERTScore} = \frac{2 \cdot Precision \cdot Recall}{Precision + Recall}
\]

With this, patches that are semantically equivalent but with different phrasing not to be penalized, but rather have a high score.
